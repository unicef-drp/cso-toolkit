Appendix E — Glossary

This glossary defines the terms the handbook uses with a precise meaning, as of cso-toolkit v0.12.0 (2026-11-24). Some carry contractual weight: a canonical deposit, for instance, is a status that depends on which role is acting, not just a place on disk. Entries are alphabetical; each links to the chapter or appendix that owns the detail. Which languages implement what is in the coverage matrix.

E.1 Adaptation (vintage)

A harmonised derivative of a master vintage, built for one collection and named by a further token block, …_v<MM>_M_v<AA>_A_<HHHH>, where v<AA>_A numbers the adaptation and <HHHH> names the collection. “Latest adaptation” is the numeric maximum for the requested collection. See The IHSN convention and the folder grammar.

E.2 Aggregation contract

The capability family that turns country-level observations into regional and global figures while accounting for the share of population the data cover. Its core is aggregate_data_v2(), with helpers for time windows, coverage footnotes and survey weights. See Aggregation.

E.3 Cache key

The short snake_case name under which dw_api_fetch() stores a response, chosen to encode what makes it distinct; it becomes the file name <cache_key>.<ext> in the frozen cache, so a reviewer can find the exact response a producer fetched. See The external-API contract.

E.4 Canonical deposit

The single authoritative copy of a project’s deposited outputs and their sidecars: for the indicator warehouse, the Teams folder 060.DW-MASTER/ and its Z: mirror. The producer writes it, the reviewer only reads it, the publisher publishes from it. The microdata archive’s Z:/datalib* trees are canonical in a separate sense, and nothing passes between the two stores. See Why a toolkit, and how it fits together.

E.5 Check record

A small file, .checks/<content-hash>.json, that sh tools/check --record commits when every local check passes on committed content, so a pull request can show its checks were run without re-running them on GitHub. See Checks and CI.

E.6 Collaboration model

The project setting, single-producer or multi-producer, that says how many people may produce results. It lives in the committed cso_project.yml (no file means single-producer) and is separate from each person’s dw_mode; in a multi-producer project dw_save() guards outputs against concurrent or unrecorded replacement. See Roles and the mode contract.

E.7 Collection

The harmonisation code in the last token of an adaptation folder name (for example HLT), naming the modules and merge keys a vintage conforms to in datalib’s registry. A domain says where a survey is shelved; a collection says how a vintage is harmonised and merged. See The IHSN convention and the folder grammar.

E.8 Contract auditor

The static check, test_scripts(), that flags direct calls to the raw file-IO and API functions the toolkit wraps, so a repository does not drift back to unwrapped IO. A trailing # cso-allow: <rule-id> comment exempts a deliberate exception. See Checks and CI.

E.9 Coverage threshold

The minimum population share, a fraction in [0, 1], that countries with data must cover for an aggregate to be reported; below it aggregate_data_v2() returns a missing value instead. The default is no threshold; 0.5 is the common UNICEF choice. See Aggregation.

E.10 Cross-language parity

The commitment that an operation has the same name and behaviour in R, Python and Stata, with one sidecar schema, the same mode-aware routing and one error shape. A parity certificate, written by sh tools/certify --record, records the shared test cases’ results in all three languages for one state of the code. See How the three languages stay in step.

E.11 Data Steward

In the draft microdata governance model, the role that operates the archive: it runs the review-gate checks, promotes conformed vintages into the canonical trees and keeps the logs, while the Microdata Core Group decides gate outcomes. The post is not yet filled. See The microdata archive.

E.12 DBM / DBR / DBP

The role acronyms: Database Manager (producer), Database Reviewer (reviewer) and Database Publisher (publisher, formerly INGESTOR). See Roles and the mode contract.

E.13 Deposit check

The rule, enforced by dw_check_deposit(), that every input a pipeline keeps out of Git has an identical copy (same SHA-256) at the same relative path in the deposit on Teams or Z:; a missing or differing file stops the run. See The IO contract.

E.14 Domain

A thematic grouping of microdata holdings, each shelved under its own library root (health under Z:/datalib-hlt, for example). The domain list is still a draft. Contrast Collection. See The microdata archive.

E.15 dw_apis_allowed

The session flag that gates external network calls: TRUE in producer mode, FALSE in reviewer mode, derived from dw_mode when the profile loads. When dw_api_fetch() finds no cached response and the flag is not TRUE, it stops before any request. See Profiles and the mode switch.

E.16 dw_mode

The session property, "producer" or "reviewer", that decides which side of the mode contract a session is on. The profile reads it once from the user’s block in ~/.config/user_config.yml, where a dw_mode_by_project entry takes precedence; there is no default, and it is never a per-call argument. See Profiles and the mode switch.

E.17 Error envelope

The shape of every deliberate error and warning in the toolkit: a [cso_toolkit.<function>] prefix naming the function that raised it, a line saying why the rule exists, and a Fix: block of numbered remedies. See Provenance sidecars and the error envelope and Appendix C.

E.18 External-API contract

The capability family that puts external data sources behind one mode-aware function, dw_api_fetch(), with the source chosen by api =. A producer fetches live and caches the response; a reviewer reads only the cache. See The external-API contract.

E.19 Frozen cache

The store of upstream API responses, <rawdata>/_apis/<api>/<cache_key>.<ext> with a sidecar each, that a reviewer re-runs against without the network; a missing response stops a reviewer’s call. “Frozen” means the response does not change under the reviewer, so a published figure can be reproduced later. See The external-API contract.

E.20 HTTPS-URL freeze

dw_use() accepting an HTTPS URL in place of a path: a producer’s first read saves the file as <host>/<path> under the frozen-cache root, with a sidecar, and later reads use that copy. Only URLs matching the profile’s dw_url_allowlist (empty by default) are accepted; a reviewer never downloads. See The IO contract.

E.21 IHSN convention

The folder-naming grammar datalib encodes, after the International Household Survey Network’s shelving pattern: country, survey, master and adaptation vintages, each vintage holding Data/, Doc/ and Programs/. Because the path names the vintage, the microdata archive records provenance in folder names rather than sidecars. See The IHSN convention and the folder grammar.

E.22 Input manifest

The table dw_fetch_inputs() returns, one row per input with its path, SHA-256 and origin. Stored in an output’s sidecar as metadata.inputs, it lets two runs be compared. See The IO contract and Appendix B.

E.23 IO contract

The capability family that gives every read and write one shape: dw_save() and dw_use() choose the format from the extension, route paths by mode, check uniqueness, write sidecars, mirror canonical writes and check canonical reads. See The IO contract and Appendix D.

E.24 isid

A uniqueness check named after the Stata command: it asserts that a set of columns identifies rows uniquely. The toolkit offers it as dw_isid() and as the isid = argument of dw_save(), where a failure blocks the write. See The IO contract.

E.25 Manifest (.toolkit_manifest.yml)

The committed YAML file in 00_functions/ that records which toolkit release a repository has vendored: the upstream repository, the pinned tag and the copied files, among other fields. See Vendoring and updates.

E.26 Master vintage

A numbered release of a survey’s cleaned data, the block _v<MM>_M after the survey stem. Vintages are integers, and “latest” is the numeric maximum, never the alphabetical one (v10 is later than v09). See The IHSN convention and the folder grammar.

E.27 Microdata archive

The governed store of survey data files: datalib’s Z:/datalib* trees, a staging area and the deposit process. It is a different data layer from the indicator warehouse in 060.DW-MASTER, and distinct from the catalogue and from datalib, the software. See The microdata archive.

E.28 Microdata catalogue

The planned metadata and discovery layer over the microdata archive, an IHSN/NADA-style index on the DDI model, to be seeded by datalib’s inventories. It is not yet built. See The microdata archive.

E.29 Mode contract

The rules for what each mode may do at every wrapped call: a producer may call APIs and write canonical paths; a reviewer may do neither, so its writes go to the sandbox and its API calls stop. The code enforces it, at each dw_save(), dw_use() and dw_api_fetch(). See Roles and the mode contract.

E.30 Module

A single survey data file within a vintage (household, for example), stored under Data/Stata/ as <vintage-folder>_<module>.dta. The collection’s registry gives each module’s level and merge keys. See The IHSN convention and the folder grammar.

E.31 Producer

The role (DBM) that owns the deposit: it refreshes API caches, runs the pipeline and writes the canonical outputs, and is the only role allowed live network access. Set with dw_mode: producer. See Roles and the mode contract.

E.32 Provenance sidecar

The <file>.provenance.json written next to each output, recording when, by whom and in which mode it was written, its SHA-256 and shape, and any caller-supplied metadata. It is what makes a deposit auditable. See Provenance sidecars and the error envelope and Appendix B.

E.33 Publisher

The role (DBP) that pushes deposits the producer has signed off and the reviewer has checked to downstream platforms such as Helix. It reads canonical and writes only outside the deposit; dw_publish() so far supports only a dry run. See Roles and the mode contract.

E.34 Review gate

The seven-item checklist a microdata deposit must pass before promotion from staging into a canonical tree, covering naming, reproducibility, licence, access and de-identification among others. The Core Group decides; the Data Steward runs the checks. See The microdata archive.

E.35 Reviewer

The role (DBR) that re-runs the pipeline from the canonical deposit, writing only to its sandbox, and compares its outputs with the deposit. It cannot write canonical paths or call external APIs; the vendored helpers and the frozen cache let it work offline. Set with dw_mode: reviewer and a sandboxRoot. See Roles and the mode contract.

E.36 Sandbox / sandboxRoot

The per-user folder a reviewer session writes into instead of the canonical deposit, set as sandboxRoot in ~/.config/user_config.yml. A profile that derives the write paths points them there in reviewer mode, so pipeline code needs no edits. See Profiles and the mode switch.

E.37 Scaffolding

The capability family that writes a project’s standard parts: a profile (create_profile()), a sector script, or a whole repository with its checks, hooks and agent files (create_official_stats_project(), create_research_project()). See Starting a repository.

E.38 Sentinel object

The variable a generated profile sets last, profile_<repo> <- TRUE, to show it loaded completely; a sector script can test it and refuse to run without it. See Profiles and the mode switch.

E.39 Staging area

The waypoint tree Z:/staging-area/<domain>/<team-folder-as-is>/ where a microdata deposit waits for review, readable by default only by the depositing unit, the Data Steward and the Core Group. It is not an archive: each deposit is promoted or turned down within a quarter. See The microdata archive.

E.40 Stock and flow

The two microdata deposit modes. Stock is existing holdings, deposited exactly as they are so current scripts keep running; flow is new work, named by the IHSN grammar from the start. See The microdata archive.

E.41 Vendoring

The toolkit’s production adoption model: a consumer repository copies the helper files into itself and pins the release in .toolkit_manifest.yml, instead of installing them or sourcing them over the network. A re-run then uses the helpers as they stood at release, offline if need be. See Vendoring and updates.

E.42 Vintage

A dated snapshot of data or code: the data vintage in a deposit’s provenance metadata, or the toolkit vintage pinned in the manifest. Vintage permanence is the guarantee that a published vintage never changes, which frozen caches and vendoring exist to keep. See Why a toolkit, and how it fits together.

E.43 Vintage sync

The capability family that keeps a vendored copy from falling silently behind: cso_toolkit_check() warns when the pin is behind, and other helpers show the differences and refresh the copies. Updating is a producer’s step; reviewer mode makes no network call and refuses updates. See Vendoring and updates.

E.44 Z: mirror

The copy of the canonical deposit on the UNICEF Azure file share, the Z: drive. A producer’s canonical write is copied there automatically, and a failed copy warns rather than undoing the write; canonical reads compare the Z: copy with Teams by size, or by SHA-256 on request. See The IO contract.
