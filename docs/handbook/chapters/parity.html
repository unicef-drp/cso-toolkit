14  How the three languages stay in step

The toolkit is written three times: in R (r/R/, the reference implementation), in Python (python/src/) and in Stata (stata/src/). It promises that the three give the same results. The coverage matrix (Appendix A) records which functions exist in which language; it cannot show that they agree. This chapter explains how agreement is checked, and how a release proves it.

14.1 Two layers of checking

CI round trip Parity certificate
Languages R and Python R, Python and Stata
What it runs one fixture through dw_use and dw_save every case in conformance/cases/ (17 at v0.12.0), and Stata’s own suites in stata/tests/
Where GitHub Actions, workflow Conformance, on every push and pull request to main and develop the producer’s machine, sh tools/certify
Files conformance/run_r.R, run_python.py, compare.py conformance/certify.py, drivers/, cases/, fixtures/
Result a pass or fail on the pull request a committed record, .parity/<content-hash>.json

The CI round trip is a fast guard on the input/output contract. The certificate is the full check, and the one a release depends on. Stata is only in the certificate: GitHub’s runners have no Stata licence (#133), so Stata runs where it is installed.

14.2 How a run works

sh tools/certify finds a Python (CSO_PYTHON, else python3, python or py -3) and runs conformance/certify.py. That script uses only Python’s standard library, so any Python 3.8 or later can run it.

  1. It reads the cases, every conformance/cases/*.json, or only those named with --cases.
  2. It runs one driver per language, passing it the list of case ids, the fixture folder and an output folder. Each driver loads the implementation from the working tree, never an installed copy:
    • R: Rscript --no-init-file conformance/drivers/driver_r.R loads r/ with devtools::load_all(). Rscript comes from CSO_RSCRIPT, the PATH, or C:/Program Files/R/R-*/bin on Windows. On Windows the run drops Git Bash’s HOME, so that R finds its own .Renviron.
    • Python: conformance/drivers/driver_python.py, under CSO_PYTHON or the interpreter running certify.py, copies python/src into a temporary package named cso_toolkit and imports that copy. The interpreter needs the toolkit’s dependencies (pandas, PyYAML and so on).
    • Stata: certify.py writes a small do-file that sets CERT_CASES, CERT_FIX, CERT_OUT and CERT_ADO, then runs conformance/drivers/driver_stata.do in batch (StataMP-64.exe /e on Windows, -b elsewhere). The driver puts stata/src first on the ado-path. Stata comes from STATA_EXE or the usual install folders.
    Each driver gets up to 30 minutes. A case that crashes writes <id>.error.txt; a driver that stops part way is judged on the outputs it did write.
  3. Each driver writes one output per case: <id>.csv for a values case, <id>.json for a json case. It also writes _versions.json, recording its language version and, for R and Python, the toolkit version it loaded; Stata’s ado files carry no version stamp, so Stata records its own version and edition.
  4. It runs Stata’s own test suites, every stata/tests/test_*.do, when Stata is found and no --cases subset was asked for (below).
  5. certify.py judges every case in every language (next sections), and every suite, and prints a table of statuses.
  6. With --record, if everything passed, it writes the certificate and commits it.

Outputs and logs (r.log, python.log, stata.log, and stata_suites/<suite>.log) stay in a temporary folder, or the one given with --out, and the run prints where.

14.2.1 Stata’s own suites

The cases check what the three languages share. Stata also has behaviour of its own to test, such as how dw_load_config reads the user block or how dw_save guards a multi-producer project, and those tests live in stata/tests/, one do-file per area. GitHub’s runners have no Stata licence, so the certificate is where they run.

Each suite runs in its own batch Stata, so one suite’s programs and globals cannot leak into the next. The verdict comes from a file, not from the log or the exit code: - Batch Stata always exits 0, whatever happened inside. - The log repeats the source. Stata echoes every line it reads, so a “PASS” string can reach the log from a comment, or from an if branch that did not run, while the suite failed. Finding “PASS” in a log proves nothing; unicefData’s QA suite once scored a failing suite green this way.

So certify.py writes a small wrapper per suite. It changes to the repository root, runs the suite under capture noisily do, and writes the return code to <suite>.result. A suite stops at its first failed assert with a non-zero code.

A plain exit part way also returns 0, so a zero code alone does not show the suite ran to the end. Every suite therefore ends with the line global cert_suite_done 1, and the wrapper records whether that line ran. --lint checks that it is the last line of every stata/tests/test_*.do.

Only execution creates the result file, so a missing one means Stata stopped or timed out (15 minutes per suite), and counts as a failure.

Suite status Meaning Blocks a certificate?
PASS the suite ran to its last line without an error no
FAIL the suite stopped with an error, r(<rc>), or returned before its last line yes
MISSING no result file: Stata stopped or timed out yes
not run Stata not requested or not found, or --cases given no, but --record refuses

stata/tests/test_dw_stata_helpers.py tests the Python helpers that Stata calls; it runs with pytest, not here.

14.3 What a case checks

A case is a small JSON file. It gives: - id and title; - the surface: the functions under test; - the kind; - the fixtures it reads; - languages: those expected to run it; - gaps and divergences (see below).

There are two kinds.

values: the data a call returns. The case lists the columns to compare, the keys that identify a row, a numeric tolerance (default 1e-9) and, optionally, the expected number of rows. - The reference is R’s output. A round-trip case sets "reference": "fixture" and compares every language, R included, with the input file itself. - Cells are compared after normalisation: - "", NA, NaN, nan, . and None all count as missing, since CSV cannot tell them apart and each language spells missing its own way; - numbers are equal when |a − b| ≤ tolerance × max(1, |a|, |b|), so 1e+05 and 100000 agree; - anything else is a string and must match exactly; - column names are compared without regard to case. - Rows are sorted by the keys before comparing, so row order never matters. A different row count is a failure.

json: a small record of what happened, compared with the expect block of the case. Examples: did the call stop, did the message carry the [cso_toolkit.<fn>] envelope, was a file written, how many rows were added. - Each key in expect must match. - Numbers compare as numbers, so 1 and 1.0 agree, and nested objects compare without regard to key order. - Extra keys in the output are ignored.

The json kind is how behaviour that has no data output is checked: refusals, guards, sidecars and lifecycle states.

14.4 Statuses

Status Meaning Blocks a certificate?
PASS output agrees with the reference or the expectation no
gap listed in the case’s gaps, and the language wrote no output no
DIVERGES listed in divergences, and the output still disagrees no
FAIL output disagrees yes
ERROR the case crashed (<id>.error.txt), or the case names the language neither in languages nor in gaps yes
MISSING the driver wrote nothing for the case yes
UPDATE-REGISTER a listed gap now writes output, or a listed divergence now agrees yes, until the entry is removed
not run language not requested (--languages), or not found no, but --record refuses

UPDATE-REGISTER keeps the register honest. When a gap closes or a divergence is fixed, the next run says so and fails until the case file is updated. A closed gap is therefore visible in the next certificate.

14.6 The certificate

sh tools/certify --record writes a certificate only when: - all three languages ran, and every case was run (no --cases); - every case is PASS, gap or DIVERGES in every language; - every Stata suite is PASS; - the certified paths have no uncommitted change.

It then commits the file on its own, with the message Parity certificate <hash>.

The name is a content hash: SHA-256 over the git trees, at HEAD, of the eight certified paths: - r/R, python/src and stata/src, the three implementations; - stata/tests, Stata’s own suites; - conformance/certify.py, conformance/cases, conformance/drivers and conformance/fixtures, the harness.

Any change to an implementation, a Stata suite, a case, a driver or a fixture needs a new certificate. Changes elsewhere keep the old one: the handbook, READMEs, NEWS, templates, CI.

The file, .parity/<content-hash>.json with schema cso_toolkit.parity/2, records: - content_hash and trees: the hash and the tree id of each certified path; - commit, created_at (UTC), created_by and platform; - versions: per language, what its driver reported (for example R version 4.6.1, Python 3.11.9, Stata 17 MP); - result (pass), summary (the count per case status) and suites_summary (the count per suite status); - cases: per case and language, the status, a note, and the SHA-256 of the output file; - stata_suites: per suite, the status and a note.

Certificates up to v0.12.1 have schema cso_toolkit.parity/1: seven certified paths, and no suites. Their hash leaves out stata/tests, so check an older tag with the certify.py of that tag.

The output hashes let anyone check, later, that a re-run produced byte-identical outputs.

sh tools/certify --verify runs no language. It recomputes the content hash and checks that .parity/<hash>.json is committed and records a pass for that hash. It reads both from git, not from the working tree, so an uncommitted certificate does not count. --verify --rev <commit> checks another commit, such as a tag about to be pushed. The Parity certificate workflow (.github/workflows/parity-certificate.yml) runs exactly this on pull requests into main, and on demand. It takes a few seconds and needs only Python and git.

14.7 Running it

sh tools/certify                              # all cases, all three languages; exit 1 on any failure
sh tools/certify --languages r,python         # a subset while developing
sh tools/certify --cases stage_lifecycle      # one or more cases (comma separated); no Stata suites
sh tools/certify --out /tmp/parity            # keep outputs in a chosen folder
sh tools/certify --record                     # all three languages; write and commit the certificate
sh tools/certify --verify                     # is there a passing certificate for this tree?
sh tools/certify --lint                       # are the case files well formed? (runs no language)

Every run first checks what --lint checks, and stops if anything is wrong: - each case file is a JSON object with the fields its kind needs (id, title, kind, fixtures and languages; columns and keys for a values case; a non-empty expect for a json case), each gaps and divergences entry has a string issue and reason, any tolerance is a non-negative number, and "reference": "fixture" comes with a fixture; - each id matches its file name, and no id is retired; - every case a committed certificate records still has a case file, or is retired; - each Stata suite ends with global cert_suite_done 1.

The Conformance workflow runs --lint on pull requests into develop and main, in its compare job (which runs once the R and Python jobs pass). --record, --verify and --lint are separate modes; give one.

Environment variables: - CSO_PYTHON: a Python with the toolkit’s dependencies, for the Python driver; - CSO_RSCRIPT: Rscript, if it is not on the PATH; - STATA_EXE: the Stata executable, if it is not in a usual folder.

On Windows, a typical call from Git Bash is:

CSO_PYTHON=/path/to/venv/Scripts/python.exe \
STATA_EXE=C:/Users/Public/Software/Stata17/StataMP-64.exe \
sh tools/certify --record

The harness has its own tests in conformance/tests/test_certify.py. They write the outputs a driver would have written and check how certify.py judges them, without running R or Stata: python -m pytest conformance/tests.

14.8 Adding a case

  1. Write conformance/cases/<id>.json, copying a case of the same kind; the id is the file name. List every language either in languages or in gaps, with the issue (or “coverage matrix”) and a one-line reason.

    An id is permanent. Certificates and the gap register name cases by id, so an id keeps one meaning for ever. When a case is removed, or changes so much that its old results no longer describe it, add its id to conformance/retired_ids.txt with the date and the reason, and give any replacement a new id. --lint fails when a case uses a retired id, and when a case some committed certificate records has disappeared without its id being retired.

  2. Add any input file to conformance/fixtures/. Prefer a small, purpose-built file that exercises the edge you care about: missing values, an all-missing group, a duplicate key.

  3. Add a function named after the id to each driver that implements it:

    • driver_r.R: an entry in the cases list;
    • driver_python.py: a function plus an entry in CASES;
    • driver_stata.do: a program named case_<id>.

    A driver that does not know an id skips it silently, so a missing driver entry shows up as MISSING.

  4. Reset any session state the case sets. The R and Python drivers’ plain() returns to a plain local session; leaking reviewer mode or a canonical root into the next case makes failures hard to read.

  5. Run sh tools/certify --cases <id>, then the full run, then --record once the code is committed.

For a json case, prefer facts that would differ if the behaviour broke: whether a file exists, whether its hash changed, which error text appeared. “No error” alone is a weak check. For example, stage_lifecycle records whether a second call re-copied the file, and the test suite separately checks that a re-copy would change the file’s modification time.

14.9 In the release checklist

A release is tagged only when sh tools/certify --verify passes on the commit being tagged, and the release notes link the certificate (chapter “Versioning and releases”). The release-prep pull request records a fresh certificate after the version stamps change, since r/R and python/src carry the version.

14.10 What it has found

The first full run, in November 2026, found three defects that had been in the toolkit since May 2026, and fixed them: - Stata’s dw_compare failed on every call: a } else { on one line. - Stata’s dw_save failed on every call that wrote a sidecar, the default: its JSON escaping expanded to invalid syntax, and the sidecar’s file write lines used a _q directive that does not exist. - R’s dw_api_fetch lacked the envelope in reviewer mode: it called a profile-only function with arguments the profile’s version does not take, so the error said “could not find function” or “unused arguments”.

It also registered two divergences, both fixed since: - Stata’s sidecar had no sha256 (#191). Fixed with #168 through Stata’s Python integration. - R read a doubled quote in CSV as two quotes (#192). data.table::fread() keeps them, a long-standing upstream limitation, so dw_use() now unescapes them.

For v0.12.0, the new cases aggregate_total and stage_lifecycle came with the Python ports of method = "total" and dw_stage. The stage_lifecycle case also caught a mistake in its own first draft: it checked the staged file’s hash after the test had already changed the source.
