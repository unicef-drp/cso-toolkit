11  Checks and CI

A repository that follows the contract still needs something that tells it when it stops following it. This chapter covers the checks a consumer repository runs before its changes merge: that no data slipped into git, that no secret did either, that the provenance sidecars it commits are well-formed, that the analysis code goes through the dw_* wrappers, that the vendored toolkit is the vintage the repository claims, and that the project’s own functions still do what their tests say.

Those checks run locally first, with one command. A committed check record proves they passed on the exact content being merged, and GitHub verifies that record in seconds without running R. The full checks run on GitHub Actions only when a repository opts in. The chapter ends with the contract auditor, test_scripts(), the check that turns the IO and API contract into a build gate.

11.1 Data stay out; their provenance goes in

The rule the rest of the chapter enforces fits in one line: data never enter git, and the provenance sidecars that say exactly which bytes each result came from always do. Data live in the deposit (the Teams folder and its Z: mirror, the microdata archive, Gitea LFS), and dw_fetch_inputs() fills a local, gitignored inputs folder from it (The IO contract). What git holds is the record: every dw_save() output carries a <file>.provenance.json sidecar with the file’s hash and, through metadata.inputs, the hashes of the inputs it was built from (Provenance and errors; fields in Appendix B). Committing the sidecars puts that record under version control while the data stay out, so a reviewer can tell from git alone which bytes produced a result, and dw_provenance_diff() can tell whether a re-run reproduced it.

A sidecar sits next to its file when the file is inside the repository but ignored: data/derived/panel.csv.provenance.json is tracked and panel.csv is not. Microdata kept outside the repository get their sidecars under data/provenance/<path>/, mirroring where the file lives, so the sidecar for S:\datalib-edu\KEN\2022\hh.dta is committed as data/provenance/S/datalib-edu/KEN/2022/hh.dta.provenance.json.

The .gitignore pattern that does this has four kinds of line, and the second is the one people drop:

data/**                       # ignore everything below data/
!data/**/                     # re-include the directories
!data/**/README.md            # then only these files
!data/**/.gitkeep
!data/**/*.provenance.json
!data/**/input_manifest.*

Git cannot re-include a file whose parent directory is excluded: it never looks inside an excluded directory, so a ! rule for a file in one is never consulted. Because data/** also matches the sub-directories, !data/**/ (the trailing slash means “directories only”) lets git look inside them again; the files there stay ignored unless a later ! line names them. For the same reason the folder rule is data/**, never data/: the latter excludes the directory itself, and nothing below it can come back.

The templates repeat the block for inputs/, _apis/ (the API cache) and _frozen/ (frozen URL downloads). They then ignore data formats wherever they appear (*.dta, *.rds, *.parquet, …), secrets and personal configuration (.env, *.pem, *.key, user_config.yml, .Renviron), and the build noise of R, Python, Stata, Quarto and LaTeX. Both re-include .checks/*.json after every rule that could ignore it, so check records are always tracked.

11.1.1 Research projects and official statistics

The two templates differ in where results live. In a research project git is the canonical store for results: the small tables and figures a reader checks the paper against are tracked, each with its sidecar.

In an official-statistics repository (a DW sector pipeline, an SDMX or data.unicef.org publication pipeline, a survey-processing repository) the canonical store is the deposit, then SDMX and data.unicef.org, and pre-release figures are embargoed. Access to the repository is not authorization to release what is in it, and git history keeps whatever was committed. So official-stats.gitignore ignores output folders outright (**/output/**, **/outputs/**, **/results/**, **/wrk/**, and **/013_wrkdata/**, the work-data stage of the deposit layout), sidecars included, and a small pre-release CSV cannot be committed by accident. The raw-data stage, **/011_rawdata/**, keeps only its READMEs, sidecars and manifests, like inputs/.

What such a repository commits instead is a release record. After publication, as part of the release pull request, it adds releases/<vintage>/output_manifest.csv (one row per deposited file with file, sha256, bytes, deposited_at and the path relative to the deposit root) and copies of the deposited files’ .provenance.json sidecars. The template re-includes exactly those files under releases/. A release record is never committed before the publication date: its hashes describe embargoed figures.

Research project Official statistics
Canonical store for results git the deposit, then SDMX / data.unicef.org
Results in the repository small tables and figures, with sidecars none; output folders ignored
Confidentiality results public with the paper embargoed until the publication date
Release record the tracked results releases/<vintage>/ manifest and sidecars, after publication
Folder layout data/, inputs/ at the root 01_dw_prep/010_metadata, 011_rawdata, 012_codes, 013_wrkdata; inputs/, _apis/, _frozen/ at any depth; releases/
Extra noise Quarto and LaTeX builds reviewer sandbox, local copies of the deposit
Tracked configuration none by default _config_template/user_config.yml

Both templates ignore a reviewer’s local artefacts, sandbox/ and the *.staged.json sidecars dw_stage() writes. The blocks they share (data formats, secrets, language noise, OS and editors) are kept identical by a test in the toolkit’s own suite, so edit both copies together.

TipCheck the rules, not your memory of them

git check-ignore -v <path> prints the line that decides a path. git ls-files -i -c --exclude-standard lists tracked files the rules now say should be ignored; after adopting a template it must print nothing. git rm --cached -- <path> untracks a file without deleting it. History still holds anything committed before. Removing it from history is a separate decision, taken with the repository owner (and the data owner, for confidential microdata), and a leaked secret is rotated first, whatever happens to history.

The ignore file is the safety net, not the first line of defence. That is the staging habit: never git add -A or git add .; stage by path (git add -- R/clean.R results/t1.csv results/t1.csv.provenance.json) and read git diff --cached --stat before committing. The checks below catch what both miss.

11.2 Design principles

Ten principles shape the checks. Each earns its place by a failure it prevents.

  1. Checks run locally first. Every check runs on your machine with one command from the repository root and prints a PASS / WARN / FAIL / SKIP line per check, exiting non-zero on any failure. GitHub Actions are opt-in and call the same script, so they add an independent run, never a different check. Actions minutes run out, and a failure reproduced on your machine gets fixed before the push.
  2. CI never needs real data. Tests use tiny synthetic fixtures. Reproduction against real data runs locally in reviewer mode, and its evidence (the dw_provenance_diff() status, dw_check_deposit() output, a dw_compare() summary) goes in the pull request. Data must not be on a hosted runner, and a check that needs data cannot run on every push. For the same reason CI never runs in producer mode: the checks put their own session in reviewer mode (tools/check.R before it loads the vendored helpers, tests/testthat.R before it sources anything), no workflow template sets dw_mode, and a job must never set dw_mode: producer, which would allow network calls and canonical writes from a runner.
  3. Default checks are fast, under ten minutes. A check people wait for gets skipped, and a pre-push hook that takes too long gets bypassed.
  4. Merges are gated by the check record. The gate is a committed record that check.R passed on the pull request’s exact content, verified on GitHub without running R (Check records) and required by branch protection. A check that can be merged around is advice, not a gate.
  5. Every bug fix ships a regression test that fails on the old code and names the issue. The bug cannot return silently, and the test records what went wrong.
  6. Least privilege, pinned actions. Workflows start from permissions: contents: read, and actions are pinned to a version. A compromised dependency should not be able to write to the repository or alter results unnoticed.
  7. No secrets in logs. Prefer checks that need no secret; scanners redact. Logs, and check output pasted into a pull request, are readable by everyone with access to the repository.
  8. Fail with an actionable message, in the toolkit’s WHAT / Why / Fix envelope (Provenance and errors). A red check that says how to turn it green costs minutes.
  9. Spend minutes where they buy something. When Actions run, default to ubuntu-latest and few jobs, since each is billed by the started minute; run Windows and macOS on a schedule or on release. Private repositories pay for minutes, and Windows minutes count double and macOS minutes ten times.
  10. CI is documentation. The README has a short section listing the checks, the local command, and which workflows are switched on.

11.3 Running the checks: tools/check

From the repository root:

sh tools/check                   # every default check
sh tools/check --record          # ... and, if none fails, commit a check record
sh tools/check --only tests      # one check (comma-separate several)
sh tools/check --skip tests      # all but one
sh tools/check --list            # the default and available names

tools/check is a small shell wrapper around Rscript --no-init-file tools/check.R, which takes the same arguments. Use --no-init-file, never --vanilla: --vanilla also drops .Renviron and the library path it sets. If Rscript is not on the PATH, as is common on Windows, set RSCRIPT to its path, or the wrapper looks in the default Windows install folder.

Windows. Started from Git Bash, R takes Git Bash’s HOME (C:\Users\<user>) as its home folder. It then misses a .Renviron that lives in Documents (often redirected to OneDrive), and with it the user library, and the checks fail with “there is no package called testthat”. tools/check therefore starts R with env -u HOME, so R falls back to Documents, and passes the original HOME as CHECK_GIT_HOME, which the git calls inside check.R get back, so git still finds user.name and user.email.

check.R needs R, git on the PATH, and the packages testthat (for tests), jsonlite (for sidecars; testthat installs it) and yaml (for vintage). When the repository has renv/activate.R, the script activates renv itself, since --no-init-file skips the project’s .Rprofile; CHECK_NO_RENV=true turns that off, as the workflows do. It prints a header line with the repository, commit (marked when there are uncommitted changes), R version and time, then one line per check, each failure with a Why: and a Fix: line, then a tally.

tools/check.R is an R script. A Python-only or Stata repository can still run the hygiene and sidecar checks with it, because they read files only and need just R and jsonlite: drop contract-audit, vintage and tests from CHECKS, and run pytest alongside.

The settings sit in one CONFIG block at the top of tools/check.R. An environment variable of the same name overrides any of them for one run, for example AUDIT_MODE=blocking sh tools/check.

11.3.2 The checks

The checks come in three tiers. Tier 0 goes in every repository, Tier 1 in every repository with code, Tier 2 when it earns its keep. The workflow column names the opt-in GitHub Actions template that runs the same check.

Tier Check tools/check.R Workflow (opt-in)
0 No data, secrets or embargoed outputs tracked outside the allowlist tracked-data ci-hygiene.yml
0 No tracked file over 50 MB large-files ci-hygiene.yml
0 Secret scan of the full history (gitleaks, redacted) secret-scan ci-hygiene.yml
0 Provenance sidecars parse and carry the core keys sidecars ci-hygiene.yml
0 Contract audit, test_scripts() on the vendored helpers contract-audit ci-contract-audit.yml
0 Toolkit vintage: manifest well-formed, cso_toolkit_check() offline vintage ci-contract-audit.yml
1 R tests (testthat; R CMD check for a package) tests ci-r-tests.yml
1 lintr (advisory) lint ci-r-tests.yml, manual runs
2 Manuscript build and page limit manuscript ci-manuscript.yml
2 Site deploy, renv status, cross-language conformance, scheduled drift checks — see docs/ci_cd_guidelines.md
  • tracked-data lists every tracked file outside ALLOW_PATHS that sits in a DATA_DIRS folder without matching DATA_ALLOW, has a DATA_EXTS extension, is a secret or personal configuration file (.env, .env.* but not .env.example, *.pem, *.key, *.p12, *.pfx, .netrc, .Renviron, user_config.yml), or sits in an OUTPUT_DIRS folder outside releases/. The fix it prints is git rm --cached -- <path>, which keeps the file on disk, plus the matching .gitignore rule.
  • large-files fails on any tracked file over MAX_FILE_MB. Git keeps every version forever, and GitHub rejects files over 100 MB. Move the file to the deposit and commit its sidecar instead.
  • secret-scan runs gitleaks git --redact over the full history. Locally it is skipped when gitleaks is not installed; in CI (CI=true) a missing gitleaks is a failure. A finding means the secret is compromised: rotate it first, then remove it from the code. A known false positive goes in .gitleaksignore, by the fingerprint from the report, with a comment saying why.
  • sidecars parses every tracked *.provenance.json and checks the shape Appendix B documents: path, format, written_at, dw_mode and a 64-character hex sha256 for an R or Python sidecar; datasignature in place of the hash for a Stata one (format dw_save.provenance/1); url, fetched_at, dw_mode and sha256 for an API-fetch or frozen-URL sidecar. It does not re-compute hashes: the data are not in the repository, so the bytes are checked locally or in reviewer mode, where dw_read_provenance(), dw_check_deposit() and dw_provenance_diff() have the files to hash. An R sidecar with no sha256 usually means the digest package was missing when it was written.
  • contract-audit loads dw_io.R and test_scripts.R from TOOLKIT_DIR, in reviewer mode, and runs test_scripts() over each folder in AUDIT_PATHS, skipping the vendored folder itself. It audits with the exact code and vintage the repository runs, not a fresh install. It fails when the vendored files or every AUDIT_PATHS folder are missing, or when AUDIT_MODE is neither blocking nor advisory. The auditor itself is described below.
  • vintage reads 00_functions/.toolkit_manifest.yml, requires source, pulled_version and vendored, confirms every vendored: file is present, and runs the vendored cso_toolkit_check() in reviewer mode, which compares against target_version offline. It fails when pulled_version is behind target_version. A newer upstream tag is not a failure: refreshing remains the producer’s decision (Vendoring and updates).
  • tests runs tests/testthat.R in a fresh R process (through renv when the repository has it), so the runner’s reviewer-mode globals do not leak into the check run. In an R package (a DESCRIPTION at the root) it is skipped with a pointer to R CMD check.
  • lint runs lintr::lint_dir(), excluding the vendored folder, renv and the test fixtures. It only ever warns, and is skipped when lintr is not installed.
  • manuscript builds PAPER_DIR/ROOT_FILE with latexmk from the committed tables and figures and fails when the PDF is over MAX_PAGES (0 turns the limit off). Without latexmk it is skipped locally and fails in CI; without pdfinfo the page count is not checked.

11.3.3 Contract audit: blocking or advisory

AUDIT_MODE decides what a contract violation does. blocking, the template’s default, fails the run. advisory lists the violations under a [WARN] line and does not fail it. Official statistics keep it blocking, because a raw read there is an input without provenance in a published figure. A research project created by create_research_project() starts advisory, because its first scripts read their data directly (haven::read_dta(), read.csv()) long before they move to dw_use(). The audit reports each such line from the first day, and the project switches to "blocking" once its code reads through the wrappers.

11.4 testthat in every R repository

A sector pipeline or a paper is not an R package, so it has no R CMD check to run its tests. The templates/testthat/ skeleton fills that gap with a runner, tests/testthat.R, that works without a DESCRIPTION. It puts the session in reviewer mode, so a test that reaches for the network or a canonical deposit fails instead of fetching; sources the vendored helpers from TOOLKIT_DIR (dw_io.R first); sources the project’s function files from SOURCE_DIRS (files that define functions, never scripts that run an analysis); and calls testthat::test_dir(), exiting non-zero on any failure. The scaffolders set SOURCE_DIRS to R/functions for a research project and leave it empty for official statistics.

  • R
  • Python
# Locally, from the repository root:
#   sh tools/check --only tests
# (or the runner on its own: Rscript --no-init-file tests/testthat.R)

# A regression test names the issue and fails on the pre-fix code.
test_that("regression #12: codes with stray whitespace or lower case are kept", {
  ind <- read_fixture("indicators_synthetic.csv")   # tiny, synthetic
  out <- merge_country_names(ind, countries)
  expect_setequal(out$TIME_PERIOD[out$country == "Kenya"], c(2021, 2022))
})

test_that("an unknown code fails loudly with a WHAT / Why / Fix error", {
  err <- expect_error(merge_country_names(bad, countries))
  expect_envelope(err, "merge_country_names")
})
# No Python skeleton ships. Use pytest with the same rules: synthetic
# fixtures under tests/fixtures/, a regression test per fixed bug named
# after the issue, errors asserted on the "[<scope>.<function>] ... Fix:"
# envelope, and the session configured with dw_mode="reviewer",
# dw_apis_allowed=False.

The example in the skeleton is the pattern to copy rather than the function to keep: a small project function, a fixture that carries the very codes that once broke it, and a test whose title names the issue. Run against the old implementation, an inner join on raw codes, the test fails; against the fix it passes. The skeleton follows the toolkit’s own suite: helpers in helper-*.R (read_fixture(), local_tempdir(), local_dw_state(), expect_envelope()), session state set through a local setter that restores on exit, and errors asserted with expect_envelope(). No Stata test runner ships; the hygiene and sidecar checks still cover a Stata repository, since they read only files.

11.5 Check records

Local-first checks leave one gap: nothing proves they were run on what gets merged. A forgotten hook, git push --no-verify, or a co-author who never enabled the hook all go unnoticed. Required status checks close that gap only by running the full checks on GitHub, which is what local-first avoids. A check record closes it at almost no Actions cost.

  • The record. sh tools/check --record runs the checks and, when none fails, writes .checks/<content-hash>.json and commits it, alone, with the message Check record <hash>. It needs a clean working tree on a commit (untracked files do not count), because a record certifies committed content: commit your changes first, and do not stash them, since worktrees share one stash list. --record refuses --only and --skip: a record never certifies a partial run. If a passing record for the content already exists, it says so and writes nothing.
  • What it holds. schema (check_record/1), content_hash, the commit and branch checked, result (pass), each check’s result in checks (pass; advisory for a WARN, such as an advisory contract audit or lint; skipped), toolkit (the manifest’s pulled_version), r_version, platform, user (git’s user.name), checked_at in UTC, and check_script_sha, the git hash of tools/check.R itself.
  • The content hash is git’s tree ID of the repository with .checks/ left out: git ls-tree HEAD | grep -v '\t.checks$' | git mktree. A record certifies content, not a commit ID, so the commit that adds the record keeps the same content hash, which avoids the chicken-and-egg problem. Computed from git objects, the hash is the same on Windows and Linux.
  • One file per checked state, about 1 KB each: records never conflict between branches, and history keeps every checked state.
  • Merging develop into a branch changes its content, so record again before pushing. A pull request whose content is identical to an already recorded state, such as the release pull request develop → main right after a feature merge, reuses that record.
  • Limits. A record can be written by hand. It prevents forgotten checks, not forgery, like any honour-based gate. Shared or mirrored repositories with different content need their own records.

11.5.1 The pre-push hook

templates/hooks/pre-push is tracked in the repository as .githooks/pre-push. Enable it once per clone:

git config core.hooksPath .githooks

The scaffolders do this for you when called with git = TRUE, and stage the hook and tools/check with their executable bit, so they run on macOS and Linux clones too.

The setting MODE at the top of the hook decides what it does, and CHECK_HOOK_MODE overrides it for one push:

  • MODE=verify (the default) requires, for each pushed branch, a passing record for the commit’s content, committed in that commit (the record must say "result": "pass"). It runs no R, so pushes stay fast. Branch deletions and tags are not checked. A refused push prints the command to run: sh tools/check --record, then push again.
  • MODE=run runs the checks instead (sh tools/check, or tools/check.R directly when the wrapper is missing), for repositories that do not use records. CHECK_ARGS="--skip tests" git push runs a subset, and RSCRIPT points at R when it is not on the PATH.

To skip the hook once, when you must, use git push --no-verify or CHECK_SKIP=1 git push, and say so in the pull request. The pull request’s check-record status still fails without a record.

11.5.2 The check-record workflow

check-record.yml is the one workflow on by default. It runs on pull requests into develop and main (and by hand), never on push. It checks out the pull request’s head commit, not GitHub’s merge commit, recomputes the content hash, and requires .checks/<hash>.json to exist and say pass; it then prints the record’s summary. It needs no R and no data, takes about 10 seconds, and has contents: read and pull-requests: read permissions. GitHub bills it as one minute on a private repository.

Automated pull requests (a bot rebuilding the handbook, a sync job) carry no record. List the generated paths they touch in the workflow’s EXEMPT_PATHS (space-separated shell patterns, where * also matches /, for example docs/handbook/*). A pull request whose every changed file matches one passes without a record. Anything that changes other files still needs one, whoever opened it.

Branch protection (Settings > Branches, for develop and main): require the status check check-record, and tick Require branches to be up to date before merging. Then what merges is exactly the checked content. The toolkit repository itself uses its parity certificate (How the three languages stay in step) and its package CI instead.

11.6 The opt-in workflows

With workflows = TRUE, the scaffolders also write the workflows that run the full checks on GitHub: ci-hygiene.yml, ci-contract-audit.yml and ci-r-tests.yml for both kinds, and ci-manuscript.yml for a research project only. Each calls tools/check.R with --only, so they run exactly the local checks, and each is configured at the top of tools/check.R, not in the YAML.

Workflow Runs Notes
ci-hygiene.yml tracked-data,large-files,secret-scan,sidecars One job, not four. Full history (fetch-depth: 0) for the secret scan. Installs a pinned gitleaks binary (8.21.2): the gitleaks GitHub Action needs a licence key for organisation repositories, the binary does not.
ci-contract-audit.yml contract-audit,vintage Installs only yaml: test_scripts() needs base R.
ci-r-tests.yml tests Restores renv.lock when there is one, otherwise installs testthat, withr, yaml and jsonlite (add your project’s packages). An advisory lintr job runs on manual runs only, with continue-on-error. A commented r-package job runs R CMD check instead, for a repository that is an R package.
ci-manuscript.yml LaTeX build and page count Builds with xu-cheng/latex-action, checks pages with pdfinfo against MAX_PAGES, and uploads the PDF as an artifact for 14 days. A commented job does the same for Quarto.

By default they run only when started by hand and on pull requests into main (the release pull request), so routine pushes cost no Actions minutes, and every release gets an independent run on a clean runner for a few minutes. The manuscript workflow also has a paths: filter on paper/**. Each workflow carries a commented on: block that switches it to every push and pull request.

They are not required checks by default: with the default triggers they do not run on pull requests into develop, and a required check that never runs blocks the merge forever. A repository that has the minutes switches each workflow’s on: block, lets the workflows run green once, and then marks the Tier 0 and Tier 1 jobs as required on develop and main. Two details matter then. GitHub matches a required check by its job name, so the templates give each job a stable name:. And a required workflow must not carry a paths: filter: when a pull request touches no matching path the workflow never runs, and its required check waits forever. Path filters belong on advisory workflows only, which is why the manuscript workflow is advisory. Windows and macOS runs belong on a schedule or on release (the commented block at the end of ci-r-tests.yml), never on every push. The gitflow itself is in docs/git_workflow.md.

11.7 The contract auditor: test_scripts()

Languages: R, Python. Stata: n/a (no Stata auditor). See the coverage matrix.

The contract says that file and network access go through a small set of wrappers: file IO through dw_save() / dw_use() / dw_compare() / dw_merge() (The IO contract), external APIs through dw_api_fetch() / dw_api_cached() (External APIs). A contract that is only documented decays. New scripts reach for read_csv() out of habit, a quick httr::GET() slips into a one-off fetch, and a reviewer approves the pull request without noticing either.

test_scripts() closes that gap. It walks a directory of analysis scripts and flags every line that calls a raw IO or HTTP function the toolkit wraps, together with the wrapper to use instead. Run interactively it is a code-review aid; with error_on_violation = TRUE it is a build gate.

The auditor and the wrappers are two layers of the same defence. The wrappers enforce the contract at the call site: once you call dw_save(), mode routing and provenance happen. The auditor enforces it at review time, catching the calls that never reached a wrapper at all.

11.7.1 What it does

For each file whose name matches pattern, the auditor reads the file line by line. Before matching, it replaces string literals with empty strings (so a URL or file name inside quotes does not trigger a rule) and strips trailing comments (so commented-out code is not flagged), while keeping any # cso-allow: directive, which it reads from the raw line. It then tests the line against every rule. A match is a violation.

It is a lexical check, not a parser: fast, with no dependencies beyond base R or pandas, but it sees text, not an abstract syntax tree. The false positives section says what that costs.

  • R
  • Python
test_scripts(
  path,
  pattern            = "\\.R$",
  recursive          = TRUE,
  ignore_files       = c("dw_io.R", "dw_api.R", "cso_toolkit_sync.R",
                         "profile_helpers.R", "test_scripts.R"),
  ignore_dirs        = c(".git", "renv", "packrat",
                         "node_modules", ".Rproj.user"),
  custom_rules       = NULL,
  error_on_violation = FALSE,
  verbose            = TRUE,
  debug              = NULL
)
test_scripts(
    path,
    pattern=r"\.py$",
    *,
    recursive=True,
    ignore_files=("dw_io.py", "dw_api.py", "cso_toolkit_sync.py",
                  "profile_helpers.py", "test_scripts.py", "_state.py",
                  "__init__.py"),
    ignore_dirs=(".git", ".venv", "venv", "env", "__pycache__",
                 ".tox", ".pytest_cache", "node_modules"),
    custom_rules=None,
    error_on_violation=False,
    verbose=True,
)

path is a directory (searched recursively unless recursive = FALSE) or a single file. The file-name pattern is matched case-insensitively. ignore_files skips the toolkit’s own implementation files, which must call the raw commands; ignore_dirs skips machinery folders (version control, dependency caches, virtual environments). Both are overridable. A path that does not exist is an error with the [cso_toolkit.test_scripts] envelope: a stop() in R, a FileNotFoundError in Python. Python reads files as UTF-8 and silently skips a file it cannot decode.

R has one extra argument, debug (default NULL, which inherits options(dw.debug)). When TRUE it prints the file count, the rule count and per-family tallies, and implies verbose; it does not change what the auditor flags.

Both return a data frame (an R data.frame, a pandas DataFrame) with seven columns: file, line, rule, family, message, suggest and snippet. An empty frame means a clean scan. The columns are stable, so a CI step can read them to post annotations or build a report. R returns the frame invisibly: assign it (v <- test_scripts(...)) to inspect it, since a bare call at the console prints the summary but not the frame. Python returns it normally.

11.7.2 The rules

Every rule has five fields: id, family, pattern, message and suggest. The family is "io" or "api", and only those two families can fail a build. The pattern is a regular expression (PCRE in R) matched against the scrubbed line. The message names the bypass and suggest names the wrapper that replaces it, so a caught read_csv does not just say that a rule matched: it says Direct CSV read and points to dw_use(name = ..., sector = ..., kind = ...).

The two registries differ because the raw calls differ by ecosystem. The R rules target base R and the tidyverse, data.table, haven, readxl / openxlsx / writexl, arrow, jsonlite, yaml, httr / httr2, rsdmx, wbstats, Rilostat and curl. They catch both the bare and the namespaced form of a call (read_csv( and readr::read_csv(), and use a negative lookbehind so that my_read_csv( or dw_save( does not match. A few rules reach further than their names suggest: io-xlsx also flags sheet enumeration (getSheetNames, excel_sheets, loadWorkbook), because dw_use(sheet = NULL) reads all sheets; io-load-save flags any save( or load(; api-httr flags GET, POST, PUT, PATCH, DELETE and httr2’s request; and api-download flags download.file and curl’s curl_download, curl_fetch_memory and curl_fetch_disk.

The Python rules target pandas (read_* and the .to_* methods), pickle, json, yaml, requests, httpx (including Client and AsyncClient), urllib, sdmx, wbgapi and wbdata. io-json flags json.dump and json.load on file handles, not json.dumps or json.loads on strings. io-open-write is a heuristic: it flags open() called with an explicit mode, read or write, as open(<path>, "<mode>") or open(..., mode="<mode>"), and leaves open(path) with no mode alone; its suggestion notes that a raw open() is fine for scratch files but should not touch warehouse paths.

11.7.3 Extending the rule set

Both implementations accept custom_rules, merged with the built-in registry. A consumer repository that wraps another data source adds a rule for it without editing the toolkit. Each custom rule supplies the same five fields.

  • R
  • Python
my_rules <- list(
  list(id      = "api-mysource",
       family  = "api",
       pattern = "(?<![a-zA-Z0-9_.])mysource_fetch\\s*\\(",
       message = "Direct mysource_fetch call bypasses the cache.",
       suggest = "dw_api_fetch(api = 'mysource', cache_key = ...)")
)
test_scripts("01_dw_prep", custom_rules = my_rules)
from cso_toolkit.test_scripts import _Rule, test_scripts

my_rules = [
    _Rule(
        id="api-mysource", family="api",
        pattern=r"\bmysource_fetch\s*\(",
        message="Direct mysource_fetch call bypasses the cache.",
        suggest="dw_api_fetch(api='mysource', cache_key=...)",
    )
]
test_scripts("01_dw_prep", custom_rules=my_rules)

A custom rule under some other family is reported but never fails a build, which makes it a way to add advisory checks.

11.7.4 Reporting and the build gate

With the default verbose = TRUE, the auditor prints a fixed-format block: a header, the file count, the violation count, then one stanza per violation with the rule id, file and line, message, offending line and suggested replacement. (It shows every column except family, which only governs the gate.) A clean run prints [OK] Clean.. The format is the same in both languages.

cso-toolkit contract audit
------------------------------------------------------------------------
Files scanned : 14
Violations    : 1

[io-read-csv] 01_dw_prep/012_codes/nt/build.R:42
  Direct CSV read.
  > df <- read_csv("raw/nt.csv")
  -> dw_use(name = ..., sector = ..., kind = ...)
------------------------------------------------------------------------

By default the function only reports. The gate is error_on_violation. When it is TRUE and at least one violation belongs to the io or api family, the function raises after printing, with the toolkit’s error envelope: the [cso_toolkit.test_scripts] prefix, the number of violations and files, up to five offending files (with “and N more”), and a Fix: line that says to replace the raw call with its wrapper or annotate a legitimate exception with # cso-allow:. In R this is a stop(), in Python a RuntimeError; either way the process exits non-zero, which is what a CI runner needs to mark the step failed.

  • R
  • Python
# Interactive: report only, inspect the frame.
v <- test_scripts("01_dw_prep/012_codes")

# CI gate: stop (non-zero exit) on any io/api violation.
test_scripts("01_dw_prep/012_codes", error_on_violation = TRUE)
# Interactive: report only, inspect the frame.
v = test_scripts("01_dw_prep/012_codes")

# CI gate: raise RuntimeError (non-zero exit) on any io/api violation.
test_scripts("01_dw_prep/012_codes", error_on_violation=True)

11.7.5 Exceptions: # cso-allow:

The contract has principled exceptions. The canonical one is the profile’s own configuration read: a profile reads user_config.yml with a raw yaml::read_yaml() / yaml.safe_load() because it bootstraps the configuration before any toolkit path resolution exists, and forcing it through dw_use() would be circular (Profiles and the mode switch).

For those, append # cso-allow: <rule-id> to the line. The auditor skips exactly the named rules on that one line; every other rule still applies to it, and every other line is still scanned. Several ids can be listed, comma-separated.

  • R
  • Python
# Profile bootstrap: the one routine legitimate raw YAML read.
config <- yaml::read_yaml(config_path)  # cso-allow: io-yaml

# Silence two rules on one line:
x <- read_csv(p)  # cso-allow: io-read-csv, io-write-csv
# Profile bootstrap: the one routine legitimate raw YAML read.
with open(config_path, encoding="utf-8") as _f:
    user_config = yaml.safe_load(_f)  # cso-allow: io-yaml

# Silence two rules on one line:
x = pd.read_csv(p)  # cso-allow: io-read-csv, io-to-csv

The generated profiles already carry these annotations, and so do a few toolkit files (the CSV read in generate_markdown_report, the fixture reader in the testthat skeleton). Two rules of discipline follow. An allow is line-scoped and rule-scoped: it never silences a whole file or a whole rule, so a stray comment cannot quietly disable the contract for a folder. And an allow is a documented exception, not a convenience: it marks a call that genuinely cannot go through a wrapper, and it asks for the reviewer’s attention rather than dodging it.

11.7.6 False positives and limits

Because the auditor matches text, it misfires in predictable ways.

  • Same name, different function. In R, any function called request(, save( or load( matches, whatever package it comes from. The Python patterns have no lookbehind, so pl.read_csv( (polars) and a project function named my_read_csv( both match io-read-csv. Rename the project function, or mark a genuine exception with # cso-allow:.
  • Aliases hide calls. import wbgapi as wb followed by wb.data.DataFrame(...) is not caught; api-wbgapi sees only the full module name. The same holds for any call reached through an alias or a variable.
  • api-fromjson-url does not fire. The rule looks for fromJSON("https://…"), but the URL is a string literal and is scrubbed before matching, so the call passes the audit. Use dw_api_fetch(api = 'json_get', ...) regardless.
  • It cannot judge a correct call. A lexical scan cannot tell whether a dw_save() uses the right sector or isid. It removes the most common, most mechanical failure, a raw call written by hand; it does not replace review.

11.7.7 Using it in CI

In a repository created by the scaffolders, the auditor is already wired: the contract-audit check runs the vendored test_scripts() over AUDIT_PATHS on every sh tools/check, and so before every push through the check record. To run it on GitHub too, copy templates/workflows/ci-contract-audit.yml to .github/workflows/ (or create the repository with workflows = TRUE). It runs the same command you can run locally:

Rscript --no-init-file tools/check.R --only contract-audit,vintage

A repository without tools/check.R can call the auditor directly. The job below uses the helpers vendored in 00_functions/, the exact code the repository runs, rather than installing the toolkit from GitHub, and lets the non-zero exit fail the build. Like the templates, it runs on manual runs and pull requests into main.

  • R
  • Python
name: contract-audit
on:
  workflow_dispatch:
  pull_request:
    branches: [main]
permissions:
  contents: read

jobs:
  audit:
    name: contract audit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: r-lib/actions/setup-r@v2
        with:
          use-public-rspm: true
      # test_scripts() needs base R only; the vendored copy is the one the repo runs.
      - name: Run contract auditor (vendored helpers)
        run: |
          Rscript --no-init-file -e 'for (f in c("dw_io.R", "test_scripts.R")) sys.source(file.path("00_functions", f), envir = globalenv()); test_scripts("01_dw_prep", error_on_violation = TRUE)'
name: contract-audit
on:
  workflow_dispatch:
  pull_request:
    branches: [main]
permissions:
  contents: read

jobs:
  audit:
    name: contract audit
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Install the vendored package's dependencies
        run: pip install pandas numpy
      - name: Run contract auditor (vendored helpers)
        run: |
          python -c "import sys; sys.path.insert(0, '00_functions'); from cso_toolkit import test_scripts; test_scripts('01_dw_prep', error_on_violation=True)"

The R job sources dw_io.R before test_scripts.R, as tools/check.R does, because the auditor uses internals defined there. The Python job installs only the package’s own dependencies, pandas and numpy; the vendored package (in 00_functions/cso_toolkit/; see Vendoring and updates) imports as cso_toolkit once 00_functions/ is on the path. Installed rather than vendored, the R package is named csotoolkit and the Python distribution cso-toolkit.

A few practical notes:

  • Keep the audit job separate from the test or build job, so a contract violation shows as a clearly labelled red check rather than hiding inside a larger failure.
  • No credentials needed. The auditor only reads source text: no network, no database, no data. It is fast and safe on every pull request.
  • Scope the path tightly. Point it at the folder that holds analysis scripts (the sector or prep folder), not the repository root, so vendored code and generated files stay out of scope on top of ignore_dirs.
  • The gate fires narrowly. Only io and api violations fail it, so the build fails on exactly the bypasses the contract forbids.
  • Report, then gate. For more than pass or fail, run the auditor once with error_on_violation = FALSE and write the frame to an artifact (a CSV, or a Markdown table), then run the gate. The first run gives a reviewer the full list with file, line, message and fix; the second turns the build red.

The toolkit’s own repository tests the auditor rather than running it: r-check.yml runs R CMD check on Ubuntu (release and devel), macOS and Windows, and the suite’s test-test_scripts.R asserts a clean frame on conforming code, catching a direct read_csv and a direct httr::GET, honouring # cso-allow:, and raising the envelope under error_on_violation = TRUE and on a missing path.

WarningSame version, not necessarily the same rules

python/pyproject.toml and r/DESCRIPTION declare the same version in each release. That is not a promise that the two registries catch the same calls: R has 16 rules and Python 19, as the table shows. If a rule matters to your contract, check that the vintage you vendored carries it in the language you use. Adding a rule can newly fail a build that was green, so rule-set changes follow the same semantic-versioning discipline as the rest of the API (Versioning and releases).

11.7.8 A note on the name

test_scripts() audits call sites; it is not a unit-test runner, despite a prefix that collides with testthat’s test_* naming. Both packages export dw_test_scripts() as an identical dw_-prefixed alias, and a future release may rename the function to something like dw_audit_scripts(). The aliases of the scaffolders are covered in Profiles and the mode switch.

11.8 How the pieces fit

The .gitignore keeps data out and the committed sidecars keep their provenance in. A handful of fast checks, none of which needs data, credentials or network, and all of which run on the author’s own machine, turn both, and the contract, into gates a pull request has to pass, and the check record proves they ran on what merges. test_scripts() checks that the analysis code honours the contract; review_profile() checks that the repository is wired to it (Profiles and the mode switch). A repository worked on with AI coding agents adds AGENTS.md, which tells every agent to run these checks before it pushes (Working with AI coding agents).
