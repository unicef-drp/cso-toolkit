5  The IO contract

Every analytics pipeline begins and ends with reading and writing files. In a shared statistical repository an unguarded read_csv or to_csv is a liability: it can silently overwrite a published deposit, leave a producer’s only copy on a laptop, read a stale file with no provenance, or let a duplicate-keyed table into the warehouse. The IO contract is the toolkit’s answer. It is a small family of paired read and write helpers, chiefly dw_save and dw_use, that wrap ordinary language-native IO with three layers of discipline: dispatch on the file extension, path routing that depends on the session mode, and a uniqueness and integrity check at the call site.

The same function names and the same behaviour hold across the languages, so a sector that runs partly in R and partly in Stata uses one mental model on both sides. Where the languages differ in a default, an argument or a format, this chapter says so. Which helper exists in which language is shown in the line under each heading and, in full, in the coverage matrix.

5.1 Terms this chapter uses

  • A canonical deposit is the permanent, published copy of a dataset. Downstream work and external users depend on it, so once it is written for a vintage it must not change.
  • Deposits live in two shared stores. Teams is the SharePoint-synced library that holds the canonical area; Z: is a network drive that mirrors it byte for byte. The toolkit treats a path under either as canonical.
  • The session mode is producer (you write new deposits) or reviewer (you read them and write only to a local sandbox). It is set once per session in user_config.yml, never per call; Profiles and the mode switch explains how, and how the profile derives the path globals the helpers resolve through.
  • The kind argument picks one of three data roots: wrk (working outputs, the global teamsWrkData), raw (inputs, teamsRawData) or meta (metadata, dwMetaData). It defaults to wrk.
  • An error envelope is the toolkit’s structured failure message: WHAT failed, WHY, and HOW to fix it. Warnings use the same shape. See Provenance sidecars and the error envelope and the error taxonomy.

5.2 Auto-dispatch by extension

dw_save and dw_use choose their writer or reader from the file extension. You never name a format; the suffix decides. Switching an output from CSV to parquet is a change to the file name, not to the code.

Extension R writer / reader Python writer / reader Stata
.csv / .tsv / .txt data.table::fwrite / fread to_csv / read_csv .csv read only
.csv.gz / .tsv.gz fwrite(compress = "gzip") to_csv(compression="gzip") —
.xlsx writexl (or openxlsx for a Workbook) / readxl openpyxl via pandas read only
.dta haven::write_dta / read_dta to_stata / read_stata read and write
.rds (R) / .pkl, .pickle (Python) saveRDS / readRDS pickle.dump / load —
.RData / .rda save() / load() — —
.parquet arrow::write_parquet / read_parquet to_parquet / read_parquet —
.json jsonlite json / to_json —
.yml / .yaml yaml PyYAML —

R’s .rds and Python’s .pkl play the same role, a fast native object dump. An .xlsx write takes a data frame, a named list or dict of data frames (one sheet each) or a pre-built workbook; in R, dw_use(..., sheet = NULL) reads every sheet into a named list.

WarningStata reads .dta, .csv and .xlsx, and writes .dta

Parquet, RDS and JSON do not dispatch on the Stata side. A pipeline that needs them routes that step through R or Python and hands Stata a .dta (or .csv). This is a design boundary: keeping the .ado helpers free of external binaries is what keeps them working under AppLocker, the Windows policy on UNICEF laptops that blocks unsigned executables.

5.3 Writing: dw_save

Languages: R, Python, Stata. See the coverage matrix.

dw_save resolves a path, optionally checks that the rows are unique, writes the file, emits a provenance sidecar and, in producer mode, copies the result to the redundant mirrors. It takes a literal path, or, more usefully, a name that it resolves through the mode-aware roots, so the same script lands in the canonical deposit in producer mode and in the local sandbox in reviewer mode with no change to the call. name is the file name, sector the sector folder ("ed", "nt", …), kind the data root, and an optional vintage adds a subfolder between sector and file.

  • R
  • Python
  • Stata
dw_save(df, path = "out.csv")
dw_save(df, name = "dw_ed_edu.csv", sector = "ed", kind = "wrk")
dw_save(df, path="out.csv")
dw_save(df, name="dw_ed_edu.csv", sector="ed", kind="wrk")
dw_save , filename("dw_ed_edu") path("$teamsWrkData/ed") idvars(REF_AREA INDICATOR)

Stata’s calling convention differs. It takes path() and filename() explicitly (a trailing .dta in the file name is dropped and added back), the folder must already exist (create it with dw_mkdir; otherwise error 601), and idvars() is required, so the uniqueness check is never optional. The R and Python name / sector / kind style is resolved by dw_resolve_path, described below.

5.3.1 The uniqueness check: isid

Pass a key tuple and dw_save checks that the declared columns uniquely identify every row before writing anything. Duplicates stop the call with their count and a sample of up to five offending rows, and the table never reaches disk. This is the toolkit’s main guard against a silently double-counted series.

  • R
  • Python
  • Stata
dw_save(df, name = "dw_ed_edu.csv", sector = "ed", kind = "wrk",
        isid = c("DATAFLOW", "REF_AREA", "INDICATOR", "SEX",
                 "WEALTH_QUINTILE", "RESIDENCE", "TIME_PERIOD"))
dw_save(df, name="dw_ed_edu.csv", sector="ed", kind="wrk",
        isid=["DATAFLOW", "REF_AREA", "INDICATOR", "SEX",
              "WEALTH_QUINTILE", "RESIDENCE", "TIME_PERIOD"])
dw_save , filename("dw_ed_edu") path("$teamsWrkData/ed") ///
    idvars(DATAFLOW REF_AREA INDICATOR SEX WEALTH_QUINTILE RESIDENCE TIME_PERIOD)

Stata uses its built-in isid, which also fails when a key variable has missing values; R and Python check duplicates only. The same check is available on its own as dw_isid.

5.3.2 Metadata and the provenance sidecar

Every successful write emits a companion <path>.provenance.json recording who wrote the file, when, in which mode, its hash and shape, and the keys checked. Appendix B lists the fields and the few that differ by language; Provenance sidecars and the error envelope explains why the sidecar exists. What you control at the call site is the descriptive metadata, which makes the sidecar self-describing:

  • R
  • Python
  • Stata
dw_save(df, name = "dw_ed_edu.csv", sector = "ed", kind = "wrk",
        metadata = list(
          title    = "Education indicators — UNICEF DW format",
          producer = "01_dw_prep/012_codes/ed/02_aggregate_uis_sdg.R",
          sources  = c("UIS bulk SDG_092025", "WPP 2024"),
          contact  = "@karavan88",
          vintage  = "2026-05"
        ))
dw_save(df, name="dw_ed_edu.csv", sector="ed", kind="wrk",
        metadata={
          "title": "Education indicators — UNICEF DW format",
          "producer": "01_dw_prep/012_codes/ed/02_aggregate_uis_sdg.py",
          "sources": ["UIS bulk SDG_092025", "WPP 2024"],
          "vintage": "2026-05",
        })
dw_save , filename("dw_ed_edu") path("$teamsWrkData/ed") ///
    idvars(REF_AREA INDICATOR)                          ///
    title("Education indicators")                       ///
    producer("01_dw_prep/012_codes/ed/example.do")      ///
    sources("UIS bulk SDG_092025")                      ///
    contact("@karavan88")                               ///
    vintage("2026-05")

In R and Python metadata is a named list or dict and may hold a data frame, such as the input manifest from dw_fetch_inputs, which is written as an array of rows. Stata has dedicated title(), producer(), sources(), contact() and vintage() options, and takes any other fields as semicolon-separated pairs: metadata("key1 value1; key2 value2"). To skip the sidecar, pass provenance = FALSE (R, Python) or nosidecar (Stata).

5.3.3 Mode-aware write routing

Reviewer mode refuses to write to a canonical deposit. A write whose resolved path lands under a canonical Teams root or under the Z: drive stops with an envelope (R stop(), Python PermissionError, Stata error 459), so a published vintage stays permanent. A Database Manager who must seed the deposit from a reviewer session passes allow_canonical_write = TRUE (Python True, Stata the allow_canonical_write option). Roles and the mode contract shows this guard and its message as the first of the two places where the mode is enforced.

Producer mode copies every deposit. A producer’s output must never live only on the producer’s laptop. In R and Python, each successful producer write is copied, with its sidecar, to the Teams canonical equivalent and the Z: equivalent of the path, whichever the profile makes available. When the primary is already in the canonical deposit (the usual case, since a producer’s working roots are the canonical roots), only the Z: copy is needed. Before writing to a non-canonical path, dw_save checks that at least one mirror is configured and stops if neither is, because the deposit would not be recoverable. A mirror copy that fails after the primary write is a warning tagged “Teams mirror” or “Z: mirror”; it does not roll back the primary. Stata’s dw_save writes only the primary .dta and its sidecar.

A legacy mirror_to_z argument is still accepted by R and Python but ignored with a deprecation warning: mirroring is automatic.

In a project set to collaboration: multi-producer, dw_save also refuses to replace an output that was changed outside dw_save or written by another user after your session started, unless you pass takeover. Roles and the mode contract describes the collaboration model and these guards.

5.3.4 The overwrite gate

dw_save will not silently replace an existing deposit, and the default depends on the language:

  • R. overwrite = NULL (the default) resolves to TRUE in reviewer mode, because the sandbox is gitignored and safe to re-run, and to FALSE in producer mode or when no mode is set.
  • Python. overwrite=False in every mode, so a reviewer re-run also needs overwrite=True.
  • Stata. No overwrite option: save, replace always replaces the primary, and the canonical deposits are protected by the reviewer-mode guard instead.

When the gate is closed, it checks every destination the write will touch (the primary and, for a producer, the Teams and Z: mirrors) and stops if any already exists (Python raises FileExistsError). Pass overwrite = TRUE to replace.

R adds one more stage. Overwriting an existing producer deposit counts as destructive even with overwrite = TRUE: interactively dw_save asks [y/N]; non-interactively it stops unless you also pass force = TRUE for a deliberate automated re-deposit.

5.3.5 Other writing behaviours

  • Atomic writes. R and Python write to a .tmp sibling and rename it into place, so a crash never leaves a half-written file under the final name. R retries the rename a few times, because OneDrive sync or a virus scan can hold the destination briefly; a file open in Excel still makes it fail. R and Python create missing folders. Stata writes with save, replace into a folder that must exist, and runs compress first unless you pass nocompress.
  • Compression. For CSV, TSV and TXT, compress = TRUE appends .gz and gzips the file. A path that already ends in .gz turns compression on by itself, so you cannot ask for .gz and get an uncompressed file.
  • CSV dialect (R). dialect = "base" writes through utils::write.table and reproduces the bytes of legacy utils::write.csv() output, for sector scripts that depend on them; the default "fwrite" uses data.table. "base" cannot be combined with compress = TRUE and says so.

5.4 Reading: dw_use

Languages: R, Python, Stata. See the coverage matrix.

dw_use is the read counterpart: the same path resolution and the same extension dispatch. R returns a tibble by default (as = "data.frame" or as = "data.table" changes that); Python returns a pandas DataFrame for tabular formats; Stata loads the dataset into memory, replacing the one there.

  • R
  • Python
  • Stata
edu <- dw_use(name = "dw_ed_edu.csv", sector = "ed", kind = "wrk")
edu <- dw_use(path = "C:/path/to/file.parquet")
edu = dw_use(name="dw_ed_edu.csv", sector="ed", kind="wrk")
edu = dw_use(path="/path/to/file.parquet")
dw_use , filename("dw_ed_edu") path("$teamsWrkData/ed")

In Stata a file name without an extension is read as .dta, and path() may be left out when filename() is a full path. Stata reads a .csv with every column as text and then converts each column that is wholly numeric, one column at a time, so one stray value leaves only its own column as a string.

5.4.1 Mode-aware read routing

Reads branch on the mode too, in the opposite direction: the goal is provenance, not protection.

  • Producer mode, or no mode (local first). Read the literal path. If it is missing and fallback_canonical is on (the default), swap the working root for its canonical one (teamsRawData for teamsRawDataCanonical, and so on) and read the canonical copy.
  • Reviewer mode (network first). Read the Teams canonical equivalent, then the Z: mirror, then the local copy. The local step warns, because a reviewer reading a local copy is reading bytes of unverified provenance. If the file is in none of the three places, dw_use stops and points the reviewer at the sector producer. fallback_canonical = FALSE (Stata nofallback_canonical) disables the local step so the read fails fast.

5.4.2 Remote URLs: fetched once, then frozen

Languages: R, Python. Stata: n/a (no remote-URL reads in Stata). See the coverage matrix.

dw_use also accepts an http(s) URL, under two rules. The URL must match a pattern in the profile’s dw_url_allowlist; an empty or unset list allows none. And the file is downloaded only once: the first read saves it under the frozen-cache root with its own provenance sidecar, and every later read uses that copy. The root is the profile’s dw_frozen_root, or <githubFolder>/_frozen, or _frozen in the working directory, in that order. Commit the frozen file and its sidecar so later runs are deterministic. A reviewer never downloads: a missing frozen copy stops with an envelope that says a producer must freeze it first.

  • R
  • Python
# In the profile:
dw_url_allowlist <- c(dw_default_unicef_allowlist(),
                      "^https://yourorg\\.github\\.io/")
dw_frozen_root   <- file.path(githubFolder, "_frozen")

# In a script:
codes <- dw_use("https://raw.githubusercontent.com/unicef-drp/<repo>/main/codes.csv")
_state.configure(dw_url_allowlist=[*dw_default_unicef_allowlist(),
                                   r"^https://yourorg\.github\.io/"])
codes = dw_use("https://raw.githubusercontent.com/unicef-drp/<repo>/main/codes.csv")

dw_default_unicef_allowlist() returns the patterns for UNICEF DRP repositories on GitHub. Live API calls are a different mechanism, covered in The external-API contract.

5.4.3 Column subsetting: strict and lenient

dw_use accepts cols to restrict the read. Whether a requested column that is missing from the file is an error depends on the format:

Format R Python Stata
.parquet, .dta error error .dta: error
.csv warns and skips it error cols() ignored
.xlsx keeps the columns present keeps the columns present cols() ignored

R adds cols_lenient = TRUE, which means “select if present”. It reads only the file’s schema (parquet metadata, or a header-only read of .dta, .csv or .xlsx), keeps the requested columns that exist, and reads all columns with a warning if none do. This gives sector scripts the intent of dplyr::any_of() inside dw_use, where calling any_of() directly fails under tidyselect 1.2.0 and later.

  • R
  • Python
  • Stata
# Strict (default): errors if a requested column is missing
df <- dw_use(path = parquet_path, cols = c("REF_AREA", "OBS_VALUE"))

# Lenient: keep only the requested columns the file has
df <- dw_use(path = parquet_path,
             cols = c("REF_AREA", "OBS_VALUE", "MAYBE_PRESENT_COL"),
             cols_lenient = TRUE)
df = dw_use(path=parquet_path, cols=["REF_AREA", "OBS_VALUE"])
dw_use , filename("dw_ed_edu.dta") path("$teamsWrkData/ed") ///
    cols(REF_AREA OBS_VALUE)

5.4.4 The Z: integrity check

When a read resolves to a canonical file and Z: is available, dw_use compares the Teams copy with its Z: mirror. By default this is a fast size check; a mismatch warns, and the read still completes with the Teams data. verify_z = "sha256" compares hashes instead, and verify_z = FALSE (Stata verify_z(off)) skips the check. Stata’s deep check compares datasignature values and works only for .dta.

Stata’s dw_use also compares the datasignature recorded in a .dta file’s sidecar with the data it has just loaded. A mismatch prints a note and the read completes; the outcome is returned in r(prov_status).

5.5 The resolver and lower-level helpers

5.5.1 dw_isid: the uniqueness check on its own

Languages: R, Python. Stata: Embedded in dw_save (no standalone command). See the coverage matrix.

The check dw_save runs is callable by itself, to validate an in-memory frame mid-pipeline:

  • R
  • Python
dw_isid(df, keys = c("REF_AREA", "TIME_PERIOD"))
dw_isid(df, keys=["REF_AREA", "TIME_PERIOD"])

On failure it stops with the duplicate count and up to five offending rows. It also catches a key column that does not exist in the data.

5.5.2 dw_verify_z: the Z: mirror check

Languages: R, Python. Stata: n/a (integrity via datasignature inside dw_use). See the coverage matrix.

dw_verify_z(path, compare = "size") returns a status rather than stopping, so the caller decides what a mismatch means: match_size, size_mismatch, match_sha256, sha256_mismatch, z_missing or no_z_mirror (and, in R, verify_unavailable when the hash cannot be computed). It is the building block behind dw_use’s automatic check.

5.5.3 dw_root and dw_resolve_path: building paths

Languages: R, Python. Stata: n/a. See the coverage matrix.

dw_root("wrk" | "raw" | "meta") returns one of the three data roots, already resolved for the current mode, so a sector script can build paths without knowing whether it runs as producer or reviewer:

final_path <- file.path(dw_root("wrk"), "nt", "2025", "dw_nut.csv")

When the profile has not set the root, R returns NA and Python returns None.

Languages: R, Python. Stata: Internal to dw_use / dw_save. See the coverage matrix.

dw_resolve_path(name =, sector =, kind =, vintage =) is the full path builder that dw_save and dw_use call internally. It also accepts path = relative to the root. It stops with an envelope when the root’s global is not set, which usually means the profile has not been sourced.

5.5.4 dw_stage: reviewer sandbox staging

Languages: R, Python. Stata: n/a (a Stata reviewer reads canonical inputs in place). See the coverage matrix.

dw_stage is an opt-in reviewer helper that copies a canonical input into the local sandbox once and hash-guards the copy with a <path>.staged.json sidecar. Outside reviewer mode it does nothing. Its lifecycle has five states:

  • First stage. The sandbox copy is missing: copy from the first available source (Z: before Teams), re-hash the copy against the source (one retry, then stop), and archive the hash.
  • Clean later run. The sandbox copy matches its archived hash: skip the copy and return the sandbox path.
  • Sandbox drift. The staged copy was changed out of band: stop with the SANDBOX DRIFT envelope.
  • Forced re-stage. overwrite = TRUE re-copies, re-checks and re-archives unconditionally.
  • Upstream changed. The canonical source has moved on: warn, but do not refresh, because rolling canonical inputs forward is the reviewer’s decision.

When both Z: and Teams hold the file, they are hash-compared before either is used; if they disagree, staging stops with a canonical-integrity error.

One known limit is tracked in open issue #226: in a reviewer session whose teamsFolder is not redirected to a sandbox, dw_stage can target the canonical folder itself. The standard profiles always redirect it.

You rarely call dw_stage directly; dw_use calls it, per call or for the session:

  • R
  • Python
df <- dw_use(name = "dw_nut.csv", sector = "nt", kind = "wrk", stage = TRUE)

# For the session, in the profile:
#   dw_autostage <- TRUE
df = dw_use(name="dw_nut.csv", sector="nt", kind="wrk", stage=True)

# For the session:
#   _state.configure(dw_autostage=True)

dw_use(..., stage = TRUE, overwrite = TRUE) passes overwrite on to force a re-stage. Staging never applies to URLs. R and Python write the same sidecar, so a file staged in one verifies in the other. The .staged.json sidecar is kept separate from dw_save’s .provenance.json, so a file both written and staged carries both; dw_stage refuses a .staged.json whose type is not dw_stage.

5.5.5 dw_fetch_inputs and dw_check_deposit: inputs kept out of Git

Languages: R, Python. Stata: Route via R or Python (#152). See the coverage matrix.

Some pipelines keep their raw inputs out of Git (Consult-tool exports, licensed microdata, large deliveries) in a gitignored folder of the repository. The copy that makes such a run reproducible is the one in the deposit, so the toolkit treats the deposit as the source of truth. The local folder mirrors a deposit folder: <repo>/<rel_dir> corresponds to <teamsFolderCanonical>/<rel_dir> on Teams and <dwZDrive>/<rel_dir> on Z:. Pass teams_root or z_root to use other roots.

dw_fetch_inputs runs at the top of such a pipeline. It:

  • lists the input files matching pattern, locally and in the deposit folder on Teams and Z:, and stops when Teams and Z: hold different versions of a file (the rule dw_stage applies);
  • copies deposit-only files into the local folder, Z: preferred, each copy SHA-256-checked and moved into place by an atomic rename, or, with copy = FALSE, returns the deposit paths to read in place;
  • with gitkeep = TRUE (the default), creates the local folder and every local or deposit subfolder with an empty .gitkeep, so the layout stays visible although the data are gitignored (the .gitignore needs !<rel_dir>/**/ and !<rel_dir>/**/.gitkeep exceptions); .gitkeep files are never inputs;
  • finishes with dw_check_deposit, so a local file missing from the deposit, or different from it, stops the run.

It returns the input manifest: one row per input with file, path (what to read), sha256, origin (local, copied from Z:, copied from Teams, read from Z: or read from Teams) and the Teams and Z: status.

Languages: R, Python. Stata: Route via R or Python (#152). See the coverage matrix.

dw_check_deposit(paths, local_root, rel_dir) can also be called on its own. A file passes when an identical copy exists on Teams or Z: and no existing copy differs, so an unmounted Z: is fine when Teams matches. stop_on_fail = FALSE returns the per-file report (match, differs, missing, no access) instead of stopping. Both functions only read the deposit and write only under the local folder, so they behave the same in producer and reviewer sessions.

  • R
  • Python
rel <- "02_consultations/023_targets/inputs"
manifest <- dw_fetch_inputs(
  local_root = file.path(projectFolder, rel),
  rel_dir    = rel,
  pattern    = "_20(23|24|25)\\.(csv|txt)$"
)
inputs <- lapply(manifest$path, readr::read_csv)
import pandas as pd
from cso_toolkit import dw_fetch_inputs

rel = "02_consultations/023_targets/inputs"
manifest = dw_fetch_inputs(
    local_root=f"{project_folder}/{rel}",
    rel_dir=rel,
    pattern=r"_20(23|24|25)\.(csv|txt)$",
)
inputs = [pd.read_csv(p) for p in manifest["path"]]

A Stata pipeline runs the fetch once from R or Python and then reads the fetched files from the local folder with dw_use.

Record the manifest in the outputs’ sidecars, with dw_save(..., metadata = list(inputs = manifest[, c("file", "sha256", "origin")])), so each output names the exact inputs it was built from; dw_provenance_diff (below) reads that record back.

5.6 Comparing and joining

5.6.1 dw_compare: what changed since the last deposit

Languages: R, Python, Stata. See the coverage matrix.

dw_compare keys two datasets on by and classifies rows as added (in current, not in reference), removed (the reverse) and changed (in both, with a differing value column). Numeric columns compare within a tolerance. R and Python treat the missing-value spellings "", "NA", "N/A", "NULL" and "." as equal; Stata compares strings exactly. R and Python return a list with a one-row summary and the added, removed and changed frames, and with write_report_to also write a CSV per part.

  • R
  • Python
  • Stata
report <- dw_compare(
  current   = dw_use(name = "dw_ed_edu.csv", sector = "ed", kind = "wrk"),
  reference = dw_use(path = file.path(teamsWrkDataCanonical, "ed/dw_ed_edu.csv")),
  by         = c("DATAFLOW", "REF_AREA", "INDICATOR", "SEX",
                 "WEALTH_QUINTILE", "TIME_PERIOD"),
  value_cols = c("OBS_VALUE", "DATA_SOURCE"),
  numeric_value_cols = "OBS_VALUE",
  write_report_to = file.path(tempdir(), "ed_compare")
)
report$summary
report = dw_compare(
    current=dw_use(name="dw_ed_edu.csv", sector="ed", kind="wrk"),
    reference=dw_use(path=ref_path),
    by=["DATAFLOW", "REF_AREA", "INDICATOR", "SEX",
        "WEALTH_QUINTILE", "TIME_PERIOD"],
    value_cols=["OBS_VALUE", "DATA_SOURCE"],
    numeric_value_cols=["OBS_VALUE"],
)
report["summary"]

The languages differ in four ways:

  • Arguments. R and Python take value_cols and numeric_value_cols; Stata takes valuevars() and decides numeric or string comparison from each variable’s storage type.
  • Tolerance. The default is 1e-5 in R and Python and 1e-8 in Stata, so set tol explicitly when it matters.
  • A first deposit. R treats a missing or unreadable reference as empty, with a warning, so every current row reports as added. Python raises FileNotFoundError for a missing reference path (pass an empty DataFrame for a first deposit), and Stata stops with error 601.
  • Output. Stata prints a console summary and, with report(), writes a short Markdown file of row counts and per-column change counts, sized for a publication-gate check.

When the counts are not enough. diagnose = TRUE adds a profile, also available on its own as dw_diff_profile(cmp, by, numeric_value_cols).

Languages: R, Python. Stata: No: r(col_changed) gives the per-column counts (#111). See the coverage matrix.

It turns “36,334 changed” into a diagnosis: which value columns differ, most first; how far each numeric column moved where it changed (absolute and relative q50, q90, q99 and max); and which key values the changed, added and removed rows concentrate on. It prints these and, with write_report_to, also writes <label>_profile.txt. In DW-Production’s ed sector this showed that an alarming mismatch was a population-weight difference, not an aggregation regression: the top column was POP_COVERAGE, every changed row was a regional aggregate, and the median relative drift was 0.01%. Stata returns the per-column counts in r(col_changed).

report <- dw_compare(result, canonical_path, by = key,
                     numeric_value_cols = "OBS_VALUE", diagnose = TRUE)
report$profile$columns     # column, n_changed
report$profile$magnitude   # abs_/rel_ q50, q90, q99, max per numeric column
report$profile$keys        # key, value, n, pct among the changed rows

Never compare a file with itself. In reviewer mode dw_use reads a sandbox path network-first from the canonical deposit, so dw_compare(sandbox_path, canonical_path) would read the deposit on both sides and report a false “0 changed”. When both arguments resolve to the same file, dw_compare stops with an envelope (#111); Stata compares the literal paths. Pass the new output as an in-memory data frame instead.

5.6.2 dw_read_provenance and dw_provenance_diff: did this run reproduce the last one?

Languages: R, Python. Stata: Route via R or Python (#152). See the coverage matrix.

Languages: R, Python. Stata: Route via R or Python (#152). See the coverage matrix.

dw_compare says which records moved. dw_provenance_diff answers the question before it, from the dw_save sidecars alone and without reading any data: did the new run reproduce the previous one? dw_read_provenance reads an output’s sidecar (or returns NULL / None when there is none); read the previous one before the new run overwrites the output. dw_provenance_diff then compares the inputs through the metadata$inputs record (file and sha256 per input, the shape of the dw_fetch_inputs manifest) and the outputs through sha256, and returns a status:

  • reproduced: the same inputs and a byte-identical output;
  • inputs_changed: input files were added, removed or changed; the three lists are returned;
  • output_changed: the same inputs but a different output, which only the code or the environment can explain; it warns with an envelope;
  • first_run: there is no previous sidecar;
  • no_input_record: a sidecar has no input record, so only the output hashes are compared.
  • R
  • Python
previous <- dw_read_provenance(out_csv)      # NULL on the first run
dw_save(result, path = out_csv, isid = key,
        metadata = list(inputs = manifest[, c("file", "sha256", "origin")]))
run <- dw_provenance_diff(previous, out_csv)
run$status                                   # e.g. "reproduced"
previous = dw_read_provenance(out_csv)       # None on the first run
dw_save(result, path=out_csv, isid=key,
        metadata={"inputs": manifest[["file", "sha256", "origin"]]})
run = dw_provenance_diff(previous, out_csv)
run["status"]                                # e.g. "reproduced"

Stata sidecars record sha256 when Stata’s Python integration is available, so dw_provenance_diff can compare Stata outputs too. It never stops on a difference; only a missing or invalid current sidecar is an error. The status is yours to act on: log it, fail a CI job on output_changed, or follow up with dw_compare.

5.6.3 dw_merge: a join that checks its cardinality

Languages: R, Python. Stata: n/a. See the coverage matrix.

dw_merge is a left join that checks its cardinality. You declare how as m:1 (the default), 1:1, 1:m or m:m, and the helper warns when the duplication of the keys on either side differs from what you declared, in either direction. That catches the silent fan-out that turns a clean join into a row explosion. using can be a data frame or a path, which is read with dw_use.

  • R
  • Python
enriched <- dw_merge(
  edu_sdg_uis,
  using = file.path(teamsRawData, "ed/metadata/regions.csv"),
  by    = "ISO3",
  how   = "m:1"
)
enriched = dw_merge(
    edu_sdg_uis,
    using=os.path.join(_state.teamsRawData, "ed/metadata/regions.csv"),
    by=["ISO3"],
    how="m:1",
)

Stata’s own merge m:1 already takes the cardinality, and stops rather than warns when the data disagree.
