12  Starting a new repository

Every repository that uses the toolkit needs the same floor before its first line of analysis: a .gitignore that keeps data out and provenance in, the local checks and the hook that requires a record of them, a test suite, the project’s collaboration setting, a home for the vendored helpers, and a README and contributing guide that tell a co-author what to do on their first clone. The chapters that follow explain each piece. This one starts a repository with all of them in one call, from the toolkit’s own templates, so a new project begins where the rest of the handbook expects it to be.

There are two functions, because there are two kinds of repository:

create_research_project() create_official_stats_project()
For a paper, an analysis, a replication package a DW sector pipeline, an SDMX or data.unicef.org publication pipeline, a survey-processing repository
Canonical store for results git: small tables and figures, each with its sidecar the deposit (Teams and Z:), then SDMX and data.unicef.org
Results in the repository committed never: embargoed until publication
What is committed after a release the results themselves; tag the submitted version a release record, releases/<vintage>/
Code lives in R/ (numbered scripts) 01_dw_prep/012_codes/<sector>/
Inputs data/ the deposit’s 011_rawdata; local copies in 01_dw_prep/011_rawdata/<sector>/ and inputs/ (filled by dw_fetch_inputs())
.gitignore research-project.gitignore official-stats.gitignore

12.1 Which one?

Ask where the results live and who may see them before publication. If the answer is “in git, and anyone with access to the repository may read them”, it is a research project. If the results are deposited and published by the office, and nobody may see a figure before its release date, it is an official-statistics repository, however small. The difference is not cosmetic: the official-statistics template ignores output folders outright, sidecars included, and its tools/check.R fails on anything tracked in them, because a pre-release table committed by accident stays in git history (Continuous integration and repository hygiene).

A paper written from official figures after their release is a research project. A research team that also runs a production pipeline keeps the two in separate repositories.

12.2 What each function writes

Both functions take the folder of the new repository and the collaboration model, which is required and has no default, as dw_mode has none: how many people may produce results is a decision for the project, not something the toolkit guesses.

The canonical raw data, API caches and promoted work data live in the deposit (Teams 060.DW-MASTER/01_dw_prep/011_rawdata and 013_wrkdata), which the profile’s teamsRawData and teamsWrkData point to in producer mode and redirect to the sandbox in reviewer mode (Wiring the contract). The repository keeps folders of the same names for local work, as DW-Production does, because a sector script made by create_sector_script() reads 01_dw_prep/011_rawdata/<sector>/ and writes 01_dw_prep/013_wrkdata/<sector>/ relative to the repository (Scaffolding and the contract auditor). Their contents never reach git: .gitignore ignores 013_wrkdata/ outright, like every output folder, and keeps only the READMEs, sidecars and manifests of 011_rawdata/; tools/check.R fails on anything tracked in 013_wrkdata/ (OUTPUT_DIRS) and on data tracked in 011_rawdata/ (DATA_DIRS). 013_wrkdata/ has no tracked file at all, so it appears with the first run. 01_dw_prep/012_codes/README.md shows how to scaffold a sector’s driver against the project’s own profile.

The .gitignore, the hook, the test helper and the workflows are the toolkit’s templates byte for byte, so the rules a repository starts with are the ones the toolkit tests. Three files are set for the kind of project: tools/check.R (an official-statistics repository gets OUTPUT_DIRS = "output outputs results wrk 013_wrkdata", the embargo check, 011_rawdata added to DATA_DIRS, and AUDIT_PATHS = "01_dw_prep/012_codes"; the contract audit is AUDIT_MODE = "advisory" in a research project, where it reports raw reads such as haven::read_dta() without failing the checks, and "blocking" in official statistics, where any of them fails; see Continuous integration and repository hygiene), tests/testthat.R (which folder of function files the tests source) and cso_project.yml (the model, today’s date and the members).

The functions never replace a file silently. Before writing anything they compare every target with what they would write: a file with the same bytes is left alone and reported as unchanged, and a file with different content stops the whole call, with nothing written, unless overwrite = TRUE. Both return the list of files with their status (written, overwritten, unchanged), so a second identical call changes nothing and says so. To adopt the conventions in an existing repository, follow Onboarding a repo, or create a scaffold in an empty folder and copy what you need.

12.2.1 The options

  • vendor, toolkit_source, toolkit_version. vendor is FALSE by default. TRUE copies the helpers into 00_functions/ from a release tag of a git clone of cso-toolkit (toolkit_source, or CSO_TOOLKIT_ROOT), and writes .toolkit_manifest.yml with that tag as pulled_version and the commit it points to as pulled_commit (The vendoring model). The tag is toolkit_version, by default the clone’s latest release tag (v0.9.1, never a pre-release such as v1.0.0-rc1). The files are read from the tag’s commit in the clone’s history, never from its working tree, so a clone on another branch or with local edits still vendors exactly the released bytes; a tag the clone does not have stops the call before anything is written (git fetch --tags first). The default set is dw_io.R, dw_api.R, cso_toolkit_sync.R, dw_provenance.R, dw_deposit.R, dw_project.R, test_scripts.R and zzz.R, plus profile_helpers.R and create_sector_script.R for official statistics; a helper of that set which the tag does not have yet (dw_project.R before the release that adds it) is skipped and named in a message. A character vector picks the files, all of which must exist at the tag, and the three that tools/check.R needs are always added. Without vendoring, tools/check.R leaves out the contract-audit and vintage checks, with a comment saying to add them back once 00_functions/ is filled.
  • workflows. FALSE by default: checks run locally. check-record.yml, which only verifies the local check record on pull requests (no R, about 10 seconds), is always written (Check records). TRUE adds the other GitHub Actions workflows, which call the same tools/check.R and by default run only when started by hand and on pull requests into main.
  • git. FALSE by default. TRUE runs git init with develop as the first branch (main is created at the first release), sets core.hooksPath to .githooks, and stages the hook and tools/check with their executable bit so they also run on macOS and Linux clones. It never commits, creates a remote or pushes.

12.2.2 The profile

Every repository gets profile_<project>.R, named after its folder, the script every analysis script and interactive session sources first, as profile_DW-Production.R is in DW-Production (Scaffolding and the contract auditor). Both kinds are written from one template, templates/profile/profile.R, and both pass review_profile() with no failure (the research profile shows one warning, for the Z: advisory it does not need):

  • it reads ~/.config/user_config.yml the way DW-Production’s template lays it out, the user’s block first (user_config[[USERNAME]]), top-level keys as a fallback;
  • it resolves dw_mode as dw_mode_by_project[["<project>"]], then dw_mode, with no default; when neither is set it stops and shows the lines to add, with the user name filled in;
  • it sources the vendored helpers from 00_functions/, zzz.R first, and reads the vintage from .toolkit_manifest.yml;
  • it never installs a package: a missing one stops the session with the list to install;
  • it resolves the collaboration model from cso_project.yml and ends with the sentinel profile_<project> <- TRUE, which sector scripts test before they run.

The official-statistics profile adds the deposit paths of Wiring the contract: teamsRawData and teamsWrkData point to Teams 060.DW-MASTER under the user’s teamsRoot for a producer, and to sandboxRoot for a reviewer, with the *Canonical aliases kept for reads; and it checks the Z: mirror with a probe that cannot hang on a disconnected drive, without stopping when the mirror is missing. Its user_config.yml keys are in _config_template/user_config.yml.

12.3 First steps for the person who created it

  1. Fill in the paragraphs the README leaves as comments: the question or the indicators, the authors, the outlet or the publication channel.
  2. Vendor the helpers if you did not (00_functions/README.md), and run Rscript --no-init-file tools/check.R. Every line should pass.
  3. Stage by path and make the first commit on develop; create main from it when you first release or circulate a version.
  4. Create the remote (private unless the project says otherwise), push both branches, make develop the default branch and protect both trunks, so changes reach them only through pull requests (docs/git_workflow.md).

12.4 First clone, for a co-author

The generated README.md and CONTRIBUTING.md carry these steps, so a co-author can follow them without this chapter:

  1. Clone, then git config core.hooksPath .githooks, once, so every push needs a passing check record (sh tools/check --record).
  2. In ~/.config/user_config.yml, under their user name, set dw_mode: reviewer. They switch to producer only for a session in which they deliberately produce or refresh results (for this repository alone: dw_mode_by_project: with the repository’s name). In an official-statistics repository they also set teamsRoot and a sandboxRoot outside the repository (_config_template/user_config.yml). source("profile_<project>.R") then tells them what is still missing.
  3. Obtain the inputs under their own licence (research) or fill inputs/ with dw_fetch_inputs() (official statistics), and verify that the bytes match the manifest: then their results are built from the same inputs.
  4. Run Rscript --no-init-file tools/check.R, and sh tools/check --record before the first push.
  5. In a multi-producer project, add their handle under members: in cso_project.yml in their first pull request.

12.5 The collaboration setting

cso_project.yml records how many people may produce results. In a single-producer project one person produces and the others review; in a multi-producer project every co-author may produce, always through a pull request, and dw_save() refuses to replace an output that was changed outside it or written by someone else during the session, unless the producer passes takeover = TRUE after checking. The setting is committed, so it is the same for everyone; a person’s dw_mode stays in their own configuration. Change it later with dw_set_collaboration(), in one reviewed pull request (Roles and the mode contract, “Collaboration model”).

12.6 Local checks first

The repository starts with checks that run on the author’s machine: tools/check.R runs every check with one command and the pre-push hook refuses a push without a passing check record, which sh tools/check --record writes after running every check. GitHub Actions are opt-in (workflows = TRUE) and run the same script; by default they run only when started by hand and on release pull requests into main, so routine work costs no Actions minutes. The pull request carries the output of tools/check.R for its head commit, and that record is the gate.
