17  Continuous integration and repository hygiene

The contract auditor chapter showed one check — test_scripts() — turning a documented rule into a build gate. This chapter widens the view to everything a consumer repository should check before its changes merge: that no data slipped into git, that no secret did either, that the provenance sidecars it commits are well-formed, that the analysis code honours the contract, that the vendored toolkit is the vintage the repo claims, and that the project’s own functions still do what their tests say. Those checks run locally first, with one command; GitHub Actions run the same script, but only when a repository opts in. The chapter also sets out how the repository’s .gitignore keeps data out in the first place, because no check can catch what the ignore rules let through unnoticed.

Everything here ships as copyable material in the toolkit repository, so a new project adopts it by copying files rather than by reading this chapter twice:

17.1 Data stay out; their provenance goes in

The rule the rest of the chapter enforces fits in one line: data never enter git, and the provenance sidecars that say exactly which bytes each result came from always do. Data live in the deposit — the Teams folder and its Z: mirror, the microdata archive, Gitea LFS — and dw_fetch_inputs() fills a local, gitignored inputs folder from it, checking each copy’s SHA-256 (see the IO chapter). What git holds is the record. Every dw_save() output carries a <file>.provenance.json sidecar with the file’s hash, schema, writer and mode, and through metadata.inputs the hashes of the inputs it was built from (Appendix B). Committing the sidecars puts that record under version control while the data stay out, so a reviewer can tell from git alone which bytes produced a result, and dw_provenance_diff() can tell whether a re-run reproduced it.

A sidecar sits next to its file when the file is inside the repository but ignored (data/derived/panel.csv.provenance.json is tracked; panel.csv is not). Microdata kept outside the repository get their sidecars under data/provenance/<path>/, mirroring where the file lives, so a sidecar for S:\datalib-edu\KEN\2022\hh.dta is committed as data/provenance/S/datalib-edu/KEN/2022/hh.dta.provenance.json.

The .gitignore pattern that implements this has four kinds of line, and the second is the one people drop:

data/**                       # ignore everything below data/
!data/**/                     # re-include the directories
!data/**/README.md            # then only these files
!data/**/.gitkeep
!data/**/*.provenance.json
!data/**/input_manifest.*

Git cannot re-include a file whose parent directory is excluded: to save time it never looks inside an excluded directory, so a ! rule for a file in one is never consulted. Because data/** also matches the sub-directories, !data/**/ (the trailing slash means “directories only”) is what lets git look inside them again; the files there stay ignored unless a later ! line names them. For the same reason the folder rule is data/**, never data/ — the latter excludes the directory itself and nothing below it can come back. The templates repeat the block for inputs/, _apis/ (the API cache) and _frozen/ (frozen URL downloads), then ignore data formats wherever they appear (*.dta, *.rds, *.parquet, …), secrets and personal configuration (.env, *.pem, *.key, user_config.yml, .Renviron), and the build noise of R, Python, Stata, Quarto and LaTeX.

17.1.1 Research projects and official statistics

The two templates differ where results live. In a research project git is the canonical store for results: the small tables and figures a reader checks the paper against are tracked, each with its sidecar. In an official-statistics repository — a DW sector pipeline, an SDMX or data.unicef.org publication pipeline, a survey-processing repository — the canonical store is the deposit (Teams and Z:, then SDMX and data.unicef.org), and pre-release figures are embargoed: access to the repository is not authorization to release what is in it, and git history keeps whatever was committed. So official-stats.gitignore ignores output folders outright (**/output/**, **/outputs/**, **/results/**, **/wrk/**, and **/013_wrkdata/**, the work-data stage of the deposit layout), sidecars included, and a small pre-release CSV cannot be committed by accident; the raw-data stage, **/011_rawdata/**, keeps only its READMEs, sidecars and manifests, like inputs/.

What such a repository commits instead is a release record. After publication, as part of the release pull request, it adds releases/<vintage>/output_manifest.csv — one row per deposited file with file, sha256, bytes, deposited_at and the path relative to the deposit root — and copies of the deposited files’ .provenance.json sidecars. The template re-includes exactly those files under releases/. A release record is never committed before the publication date: its hashes describe embargoed figures.

Research project Official statistics
Canonical store for results git the deposit, then SDMX / data.unicef.org
Results in the repository small tables and figures, with sidecars none; output folders ignored
Confidentiality results public with the paper embargoed until the publication date
Release record the tracked results releases/<vintage>/ manifest and sidecars, after publication
Folder layout data/, inputs/ at the root 01_dw_prep/010_metadata, 011_rawdata, 012_codes, 013_wrkdata; inputs/, _apis/, _frozen/ at any depth; releases/
Extra noise Quarto and LaTeX builds reviewer sandbox, local copies of the deposit
Tracked configuration none by default _config_template/user_config.yml

Both templates ignore a reviewer’s local artefacts — sandbox/ and the *.staged.json sidecars dw_stage() writes — and the blocks they share (data formats, secrets, language noise, OS and editors) are kept identical by a test in the toolkit’s own suite. docs/gitignore_guidelines.md has the full comparison.

TipCheck the rules, not your memory of them

git check-ignore -v <path> prints the line that decides a path. git ls-files -i -c --exclude-standard lists tracked files the rules now say should be ignored — after adopting a template it must print nothing. git rm --cached -- <path> untracks a file without deleting it. History still holds anything committed before; removing it from history is a separate decision, taken with the repository owner (and the data owner, for confidential microdata), and a leaked secret is rotated first, whatever happens to history.

The ignore file is the safety net, not the first line of defence. That is the staging habit: never git add -A or git add .; stage by path (git add -- R/clean.R results/t1.csv results/t1.csv.provenance.json) and read git diff --cached --stat before committing. The checks below are the backstop that catches what both miss.

17.2 Design principles

Ten principles shape the menu. Each earns its place by a failure it prevents.

  1. Checks run locally first. Every check in the menu runs on your machine with one command from the repository root, Rscript --no-init-file tools/check.R, which prints a PASS / FAIL / SKIP line per check and exits non-zero on any failure. sh tools/check --record also commits a check record of the result, and the pre-push hook refuses a push without one. GitHub Actions are opt-in and call the same script, so they add an independent run, never a different check. Actions minutes run out, and a failure reproduced on your machine gets fixed before the push.
  2. CI never needs real data. Tests use tiny synthetic fixtures. Reproduction against real data runs locally in reviewer mode, and its evidence — the dw_provenance_diff() status, dw_check_deposit() output, a dw_compare() summary — goes in the pull request. Data must not be on a hosted runner, and a check that needs data cannot run on every push.
  3. Default checks are fast, under ten minutes. A check people wait for gets skipped, and a pre-push hook that takes too long gets bypassed.
  4. Merges are gated by the check record. The gate is a committed record that check.R passed on the pull request’s exact content, verified on GitHub in seconds without running R (see Check records), and required by branch protection. A check that can be merged around is advice, not a gate.
  5. Every bug fix ships a regression test that fails on the old code and names the issue. The bug cannot return silently, and the test records what went wrong.
  6. Least privilege, pinned actions. Workflows start from permissions: contents: read; actions are pinned to a version. A compromised dependency should not be able to write to the repository or alter results unnoticed.
  7. No secrets in logs. Prefer checks that need no secret; scanners redact. Logs, and check output pasted into a pull request, are readable by everyone with access to the repository.
  8. Fail with an actionable message, in the toolkit’s WHAT / Why / Fix envelope (see the provenance and errors chapter). A red check that says how to turn it green costs minutes.
  9. Spend minutes where they buy something. When Actions run, default to ubuntu-latest and few jobs (each is billed by the started minute); run Windows and macOS on a schedule or on release. Private repositories pay for minutes, and Windows minutes count double and macOS minutes ten times.
  10. CI is documentation. A short README section listing the checks, the local command, and which workflows are switched on.

17.3 The default menu

The checks come in three tiers. Tier 0 goes in every repository; Tier 1 in every repository with code; Tier 2 when it earns its keep. Every row runs locally as a named check of tools/check.R; the workflow column is the opt-in GitHub Actions template that runs the same check.

Tier Check tools/check.R Workflow (opt-in)
0 No data, secrets or embargoed outputs tracked outside the allowlist tracked-data ci-hygiene.yml
0 No tracked file over 50 MB large-files ci-hygiene.yml
0 Secret scan of the full history (gitleaks, redacted; skipped locally without gitleaks) secret-scan ci-hygiene.yml
0 Provenance sidecars parse and carry the core keys sidecars ci-hygiene.yml
0 Contract audit, test_scripts() on the vendored helpers contract-audit ci-contract-audit.yml
0 Toolkit vintage: manifest well-formed, cso_toolkit_check() offline vintage ci-contract-audit.yml
1 R tests (testthat; R CMD check for a package) tests ci-r-tests.yml
1 lintr (advisory) lint ci-r-tests.yml, manual runs
2 Manuscript build and page limit (advisory) manuscript ci-manuscript.yml
2 Site deploy, renv status, cross-language conformance, scheduled drift checks — see docs/ci_cd_guidelines.md

By default the workflow templates run only when started by hand and on release pull requests into main, so routine pushes cost no Actions minutes. Each carries a commented on: block that switches it back on for every push and pull request.

Three of the Tier 0 checks lean on earlier chapters. The sidecar check validates the shape Appendix B documents: path, format, written_at, dw_mode, and a 64-character hex sha256 for an R or Python sidecar; datasignature in place of the hash for a Stata one; url, fetched_at, dw_mode and sha256 for an API-fetch sidecar. It does not re-compute hashes: the data are not in the repository, so the bytes are checked locally or in reviewer mode, where dw_read_provenance(), dw_check_deposit() and dw_provenance_diff() have the files to hash. The contract audit is the job the contract auditor chapter sketched, with one change: it sources the helpers vendored in 00_functions/ instead of installing the toolkit from GitHub, so CI audits with exactly the vintage the repository runs (the vendoring model). One setting at the top of tools/check.R decides what a violation does: AUDIT_MODE = "blocking" (the template’s default) fails the run, and AUDIT_MODE = "advisory" lists the violations as a [WARN] line without failing it. Official statistics keep it blocking, because a raw read there is an input without provenance in a published figure. A research project created by create_research_project() starts advisory, because its first scripts read their data directly (haven::read_dta(), read.csv()) long before they move to dw_use(): the audit reports each such line from the first day, and the project switches to "blocking" once its code reads through the wrappers. An environment variable of the same name overrides the file for one run (AUDIT_MODE=blocking Rscript --no-init-file tools/check.R). The vintage check reads .toolkit_manifest.yml, confirms every vendored: file is present, and runs cso_toolkit_check() in reviewer mode, failing when pulled_version is behind target_version. A newer upstream tag is not a failure — refreshing remains the producer’s decision (versioning and releases).

17.4 testthat in every R repository

A sector pipeline or a paper is not an R package, so it has no R CMD check to run its tests. The templates/testthat/ skeleton fills that gap with a runner, tests/testthat.R, that works without a DESCRIPTION: it puts the session in reviewer mode (so a test that reaches for the network or a canonical deposit fails instead of fetching), sources the vendored helpers and the project’s function files, and calls testthat::test_dir(), exiting non-zero on any failure. tools/check.R runs it as its tests check, locally and, when switched on, in CI.

  • R
  • Python
  • Stata
# Locally, from the repository root:
#   Rscript --no-init-file tools/check.R --only tests
# (or the runner on its own: Rscript --no-init-file tests/testthat.R)

# A regression test names the issue and fails on the pre-fix code.
test_that("regression #12: codes with stray whitespace or lower case are kept", {
  ind <- read_fixture("indicators_synthetic.csv")   # tiny, synthetic
  out <- merge_country_names(ind, countries)
  expect_setequal(out$TIME_PERIOD[out$country == "Kenya"], c(2021, 2022))
})

test_that("an unknown code fails with a WHAT / Why / Fix error", {
  err <- expect_error(merge_country_names(bad, countries))
  expect_envelope(err, "merge_country_names")
})
# No Python skeleton ships yet. Use pytest with the same rules:
# synthetic fixtures under tests/fixtures/, a regression test per fixed
# bug named after the issue, errors asserted on the
# "[<scope>.<function>] ... Fix:" envelope, and the session configured
# with dw_mode="reviewer", dw_apis_allowed=False.
* No Stata test runner ships. Stata code is covered by the conformance
* harness where it applies and by review; the hygiene and sidecar checks
* still run, since they read only files.

The example in the skeleton is the pattern to copy rather than the function to keep: a small project function, a fixture that carries the very codes that once broke it, and a test whose title names the issue. Run against the old implementation — an inner join on raw codes — that test fails; against the fix it passes. The skeleton follows the toolkit’s own suite: helpers in helper-*.R, session state set through a local setter that restores on exit, errors asserted with expect_envelope().

17.5 Check records

Local-first checks leave one gap: nothing proves they were run on what gets merged. A forgotten hook, git push --no-verify, or a co-author who never enabled the hook all go unnoticed. Required status checks close that gap only by running the full checks on GitHub, which is what local-first avoids. A check record closes it at almost no Actions cost (#174).

  • The record. sh tools/check --record runs the checks on a clean working tree and, when none fails, writes .checks/<content-hash>.json and commits it, alone. It holds each check’s result (pass, advisory for an advisory contract audit, skipped), the commit and branch, the R and toolkit versions, the platform, the user, the UTC time, and the hash of check.R itself. --record refuses --only and --skip: a record never certifies a partial run.
  • The content hash is git’s tree ID of the repository with .checks/ left out: git ls-tree HEAD | grep -v '\t.checks$' | git mktree. A record certifies content, not a commit ID. The commit that adds the record keeps the same content hash, which avoids the chicken-and-egg problem. Computed from git objects, the hash is the same on Windows and Linux.
  • One file per checked state, about 1 KB each: records never conflict between branches, and history keeps every checked state.
  • The pre-push hook (MODE=verify, the default) requires, for each pushed branch, a passing record committed in that commit. It runs no R, so pushes stay fast. MODE=run at the top of .githooks/pre-push restores the older behaviour, running the checks, for repositories that do not use records.
  • The workflow check-record.yml is the one workflow on by default: on pull requests into develop and main, never on push. It checks out the pull request’s head commit (not GitHub’s merge commit), recomputes the hash and requires the record to say pass. No R, no data, about 10 seconds, contents: read; GitHub bills it as one minute on a private repository.
  • Branch protection (Settings > Branches, for develop and main): require the status check check-record, and Require branches to be up to date before merging. Then what merges is exactly the checked content.
  • Merging develop into a branch changes its content, so record again before pushing. The release pull request develop → main reuses the record of the last feature branch whenever the trees are identical.
  • Automated pull requests (a bot rebuilding the handbook, a sync job) carry no record. List the generated paths they touch in the workflow’s EXEMPT_PATHS (shell patterns, for example docs/handbook/*): a pull request whose every changed file matches passes without a record. Anything that changes other files still needs one, whoever opened it.
  • Limits. A record can be written by hand. It prevents forgotten checks, not forgery, like any honour-based gate. Shared or mirrored repositories with different content need their own records.

Windows. Started from Git Bash, R takes Git Bash’s HOME (C:\Users\<user>) as its home folder. So it misses a .Renviron that lives in Documents (often redirected to OneDrive), and with it the user library: the checks fail with “there is no package called testthat”. tools/check starts R with env -u HOME, so R falls back to Documents, and passes the original HOME as CHECK_GIT_HOME, which the git calls inside check.R get back, so git still finds user.name and user.email.

create_research_project() and create_official_stats_project() write the wrapper, the hook, the workflow and .checks/README.md, and print the branch-protection steps; they do not change repository settings. cso-toolkit itself uses its parity certificate (Appendix G) and its package CI instead.

17.6 Gating merges and the gitflow

The check record above is the gate (see docs/git_workflow.md for the gitflow itself). The release pull request into main also triggers the opt-in workflows, which gives every release an independent run on a clean runner for a few minutes of Actions time.

The opt-in workflows are not required by default: with the default triggers they do not run on pull requests into develop, and a required check that never runs blocks the merge forever. A repository that has the minutes switches each workflow’s on: block to every push and pull request, lets the workflows run green once, and then marks the Tier 0 and Tier 1 jobs as required on develop and main. Two operational details matter then. GitHub matches a required check by its job name, so the templates give each job a stable name:. And a required workflow must not carry a paths: filter: when a pull request touches no matching path the workflow never runs, and its required check waits forever. Path filters belong on advisory workflows only, which is why the manuscript template is advisory.

The contract auditor made one rule enforceable; this chapter makes the rest of the repository’s floor enforceable in the same way. The .gitignore keeps data out, the committed sidecars keep their provenance in, and a handful of fast checks — none of which needs data, credentials or network, and all of which run on the author’s own machine — turn both, and the contract, into gates a pull request has to pass.
