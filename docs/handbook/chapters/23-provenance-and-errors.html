4  Provenance sidecars and the error envelope

Two small conventions make cso-toolkit outputs trustworthy and its failures readable. The provenance sidecar is a small JSON file written next to every data artefact, recording who wrote it, when, in what mode and with what content hash. The error envelope is a fixed three-part shape that every deliberate error and warning in the toolkit follows, so a failure reads like an instruction rather than a stack trace. Both hold in R, Python and Stata. This chapter explains why each exists and what it guarantees. The fields of the sidecar are listed in Appendix B, and the messages the toolkit raises are catalogued in Appendix C.

4.1 The provenance sidecar

Whenever you write a data file through dw_save (The IO contract), the toolkit also writes <path>.provenance.json beside it: write dw_ed_edu.csv and you also get dw_ed_edu.csv.provenance.json. The sidecar is a receipt about the data, readable by a person and by a program, that travels with the artefact into the canonical Teams folder and its Z: mirror.

4.1.1 Why a sidecar at all

The toolkit exists so that someone other than the author can reproduce an analysis (Why a toolkit, and how it fits together). Reproducibility is not only being able to re-run a pipeline; it is also being able to trust a frozen artefact two years after it was deposited. A reviewer who opens dw_ed_edu.csv from the deposit needs answers the file itself cannot give. Who produced it? In which session mode, producer or reviewer (Roles and the mode contract)? Has it been altered since it was written? What shape was it, and which inputs fed it? The sidecar answers these without touching the data file’s own schema.

The toolkit keeps this record beside the file rather than inside it (as Stata’s char _dta[] or a Parquet key-value footer would). A sidecar wins on three counts:

  • It works for every format. The same scheme serves CSV, Parquet, DTA, XLSX, JSON and YAML.
  • It never changes the artefact’s bytes. A content hash of the data file stays stable however rich the metadata grows.
  • It is easy to review. A sidecar diffs cleanly in a pull request and can be dropped when unwanted.

4.1.2 What it guarantees

The hash describes the bytes on disk. The sidecar is written after the primary file lands, and its sha256 is computed by reading that file back, not from the object in memory. That makes the hash an integrity anchor. Re-hash the file later and compare: a match means the bytes are the ones that were written; a mismatch means someone changed the file outside the toolkit. The toolkit uses this anchor itself. dw_use compares the Teams copy of a canonical file with its Z: mirror on every read, and dw_verify_z does the same on demand (The IO contract). In a multi-producer project, dw_save refuses to replace a file whose bytes no longer match its sidecar (Roles and the mode contract).

Each copy carries its own receipt. When a producer write fans out to the Teams and Z: mirrors, the sidecar is copied with it, so every copy of the artefact can be checked on its own.

Two runs can be compared without reading the data. If the caller records the inputs in the sidecar’s metadata (one record per input file with its SHA-256, which is what dw_fetch_inputs returns), then two sidecars of the same output show whether a new run reproduced the old one: same inputs and the same output hash, or which inputs changed, or (the case that warns) the same inputs but a different output, which only the code or the environment can explain. dw_read_provenance and dw_provenance_diff do this (The IO contract).

The record lives in git while the data stay out. Data live in the deposit; the sidecars that say which bytes each result came from are committed. A reviewer can then tell from the repository alone what produced a result (Checks and CI).

A sidecar never costs you the data. If the metadata hold a value that cannot be written as JSON (an R Date, a NumPy scalar), the sidecar write emits a warning and the primary file stays. The sidecar is metadata about the asset; the asset is what matters. You can also turn the sidecar off for one call (provenance = FALSE; nosidecar in Stata).

4.1.3 Two shapes, one intent

The sidecar dw_save writes describes a write event: the file, its format, its schema, its writer and its hash. When dw_use downloads an allowlisted URL and freezes it for reviewers (a producer-only step; see The external-API contract), it writes a sidecar of a different shape that describes a fetch event: the URL, the hash, the size, and who fetched it and when. Both use the .provenance.json extension and the same hashing, but their keys differ, so do not read one with a parser written for the other.

Stata writes the same sidecar with the same intent, but one difference matters. Stata records the file’s sha256 only through its Python integration (Stata 16+). It always records its native datasignature as well, and without Python that is the only hash. A datasignature is a checksum of the dataset’s values, not of the file’s bytes, so it can never be compared with an R or Python sha256. Appendix B sets out this and the smaller Stata differences field by field.

4.2 The error envelope

The toolkit’s second convention governs failure. Every deliberate stop() in R, every raise in Python and every error message in Stata follows one shape:

[cso_toolkit.<fn>] WHAT happened
  Why it happened / why the rule exists.
  Fix:
    1. The first concrete remedy, OR
    2. An alternative remedy / escape hatch.

The bracketed prefix names the function that raised: [cso_toolkit.dw_save], [cso_toolkit.dw_use], [cso_toolkit.dw_api]. The body says why the rule exists rather than restating the symptom. The Fix: block lists what to do next, often ending with the deliberate escape hatch for when you really do mean to do the forbidden thing.

4.2.1 Why one shape

One shape on every error buys three things.

  1. Searchability. The prefix is a stable token you can grep. To find every place in a consumer project that can trip the reviewer-mode write guard, search for [cso_toolkit.dw_save] Reviewer mode forbids. The library’s errors become an index.
  2. Actionability. Because Fix: is mandatory, an error never leaves you knowing what broke without knowing how to proceed. The escape hatch (allow_canonical_write = TRUE, overwrite = TRUE, takeover = TRUE, switching dw_mode) appears at the point of failure, not in a manual.
  3. Triage. A failure prefixed [cso_toolkit.*] is a decision the toolkit made on purpose, usually the contract doing its job rather than a bug. An unprefixed error is something leaking from arrow, haven, pandas or the operating system.

4.2.2 Reading one

The reviewer-mode write refusal, shown in full in Roles and the mode contract, is the envelope at its fullest, and every clause does work. The prefix names dw_save. The WHAT line names the rule and the offending path. The Why line gives the reason the rule exists, vintage permanence: a deposited vintage must never change under the people who rely on it. The Fix block gives the ordinary remedy first (write to your sandbox) and the deliberate override second (allow_canonical_write = TRUE, for a Database Manager’s bootstrap). The numbered options are ranked the same way everywhere: option 1 is the expected remedy, and a later option is usually the escape hatch.

4.2.3 Warnings wear it too

The shape is not kept for fatal errors. Non-fatal warnings use it too, including the ones the sidecar machinery emits. A sidecar that cannot be written warns with [cso_toolkit.dw_save] Provenance sidecar write failed for <path>, says the primary file is unaffected, and tells you how to make the metadata serialisable. A reviewer whose canonical and Z: locations are unreachable, and who falls back to a repository-local copy, gets a [cso_toolkit.dw_use] warning that the fallback breaks provenance and that Teams or Z: should be re-mounted before the output is relied on. The envelope makes even a soft degradation legible.

4.2.4 A tested invariant

The envelope is not only a style guide. The R test suite asserts it with an expect_envelope() helper, which checks for the [cso_toolkit.<fn>] prefix and a Fix: block on each raise the tests trigger; a raise that loses either fails the suite. Python has a script that checks the same on its raise paths, run by hand. Stata keeps the prefix everywhere, but the body is fuller in some commands than others: dw_require_no_api prints the full WHAT / Why / Fix, while the dw_save reviewer-mode refusal fits on one line that names the rule and the -allow_canonical_write- override. Stata’s adherence is kept by convention and review. Consumer repositories assert their own errors the same way (Checks and CI); the details of each test are in Appendix C.

4.3 How the two conventions reinforce each other

The sidecar and the envelope are two halves of one reproducibility contract. The sidecar makes a successful write describe itself and be checkable afterwards: who, when, in which mode, with what hash and what shape. The envelope makes an unsuccessful operation explain itself at the moment it happens: which function, which rule, why, and how to proceed.

They also lean on each other. Several of the toolkit’s stops are decisions taken by reading a sidecar: the multi-producer guards in dw_save, which compare a file’s bytes with its recorded sha256 and its writer with the current session; the dw_stage stop when a reviewer’s staged copy no longer matches the hash archived beside it; and the warning from dw_provenance_diff when the same inputs gave a different output. Each of those reaches you as an envelope whose Fix points back at the record (check the sidecar’s user and written_at, re-run, or override and have the override recorded in the new sidecar). The sidecar supplies the evidence; the envelope turns it into a decision you can act on.

Together they ensure that a cso-toolkit artefact is never a bare file of unknown origin and a cso-toolkit failure is never a bare exception of unknown cause, in whichever of the three languages a consumer repository uses.
